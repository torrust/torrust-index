# The Assayer's testing architecture · `rep:assayer:testing-architecture`

_What the package's testing scaffolding is, as it stands. Two trees carry it: the library harness under the `testing` module, compiled into the library itself, and a private support tree compiled into the `multi_channel` integration binary alone. This report describes both — how each is reached, what each owns, and what each declares — and stops where the individual tests begin: what a test asserts is written where the test is, and the catalogue that indexes those statements is elsewhere (`reg:assayer:integration-test-catalogue`)._

## How the harness reaches its callers · `sec:assayer:testing-architecture-reach`

The harness lives in the library rather than beside the tests, and three mechanisms put it there.

The first is a feature. `test-support` is off by default and pulls in exactly one dependency, the tracing subscriber a scenario's span is written through. It is what decides the `testing` module's visibility: under `any(test, feature = "test-support")` the module is `pub` and `#[doc(hidden)]`; otherwise it is `pub(crate)`. A host build therefore cannot name the module at all, which is opacity carried structurally rather than by review (`dec:surface:guidance-opacity`).

The second is a self dev-dependency. The package depends on itself by path with `test-support` enabled, so every test build of the crate — unit, crate-level and integration alike — links a library that has the feature on, while a host resolving the package from the registry gets one that does not. Nothing in the test tree has to ask for the feature, and nothing outside the test tree can obtain it by accident.

The third is the gate inside the module. Only `testing::clock` compiles unconditionally, because production reads its time through `Clock` in every build. Twenty-five submodules carry the same `cfg` the visibility does, so a sealed build compiles the clock and nothing else rather than compiling a crate-private harness that no caller can reach; gating what compiles is what retired the module-wide `dead_code` allowance a visibility-only gate would still need. Three carry a stricter gate, because durable state is itself a feature: `testing::fork` compiles when `serde` is enabled and the harness is reachable, while `testing::durable_projection` and `testing::durable_value` compile only for the crate's own test build with `serde` enabled. An integration target therefore reaches the persistence fork and never the projection that compares its arms.

Within the module, a small named set of submodules is itself `pub` — `testing::dimensions`, `testing::maintenance`, `testing::performance`, `testing::registrations`, `testing::signals` — because callers name the path and not only the item. The remaining modules are private and flattened through `pub use`, so a caller writes `testing::World` rather than `testing::world::World`; three production types travel with them, `FeatureSelector` and `InteractionTemplate` from the feature layer and `CompetitiveCellId` from the identity layer, so a scenario declaring interactions or cells needs no second import path. What stays behind the boundary is state a caller has no business naming: `names::NameRegistry` is `pub(super)`, owned by `World` and never handed out, and the durable comparison is crate-internal — `DurableProjection` and the checkpoint reader it captures through are `pub(crate)`, their serializer and the fork's storage root are `pub(super)`.

Three test caller surfaces reach the result, not two. The crate's own test tree holds fifty-eight modules and mints under `test:crate:`; the integration tree holds twenty-four targets and mints under `test:integration:`; and thirteen production source files carry inline test modules that reach `crate::testing` directly and mint under `test:unit:`. Every integration target that carries a witness reaches the harness, and the three that do not are the empty convergence targets waiting for theirs (`dec:harness:convergence-split`).

## The scenario and the World · `sec:assayer:testing-architecture-scenario`

A scenario is a `World` and a tracing span bound into one value. `Scenario` declares the world first and the span guard second, so Rust's declaration-order drop runs the world's shutdown — which joins the engine's threads — while the span is still open; the span's close event therefore times the whole scenario including shutdown rather than stopping at the last statement of the test body. `Scenario` derefs to `World` in both directions, so a test that opens with one `let` reads afterwards as though it held the world directly.

Three constructors build one. `scenario` takes an instance id and a seed and wraps `World::cold`, which declares a single `"default"` channel under the default policy. `scenario_with` adds a builder closure and supplies the harness's own infrastructure configuration. `scenario_with_config` takes the whole `AssayerConfig` for fixtures that need to tune it. All three install the subscriber through `init_tracing`, whose installation is idempotent: the first scenario in a binary wins and the rest are no-ops. Each also names itself to the construction guard, so a refusal says which constructor failed to reproduce its declaration.

The `World` is the one top-level context the rest of the harness hangs off (`dec:harness:single-scenario`). It owns a real `Assayer` — there are no mocks anywhere in the harness (`dec:harness:real-engine`) — a `VirtualClock` shared with that engine, a `TestRng`, the `NameRegistry`, a host-side bundle of channel policies with a challenge-effectiveness tracker and an assessment-to-channel map, a `Tolerances` value, the optional expected runtime layout declared for the scenario, and the complete construction declaration derived from the builder's inputs. Under `serde` it owns two more: the builder it was built from, so a fork cannot silently change its schema or policies, and the restored arm's storage root, declared last so the engine's threads shut down before their files are removed. `WorldBuilder` requires an explicit seed and returns `WorldBuildError::MissingSeed` when it is absent, because reproducibility is a construction contract rather than a default. It forwards interaction templates to the engine's validator, retains any expected layout for the scenario's published-width guard, and takes checkpoint and journal directories through `WorldBuilder::persistence_dirs` for the scenarios that need durability. Channel ids are assigned in declaration order starting at zero, and a malformed policy panics at declaration because a host's own well-formedness check is at policy load (`dec:derivation:ordered-actions`).

The ordinary lifecycle verbs — registering and deregistering a Sentinel, an outcome axis or an identity dimension — all end on a private `settle`. The engine's registration path is fire-and-forget and the record declines to promise freshness (`cor:concurrency:reader-obligations`), so a scenario that registers and then assesses has no engine-side guarantee that the assessment sees the registration. `settle` obtains one: it sends the checkpoint marker down the first-in-first-out command channel, and the marker is acknowledged only once everything enqueued before it has been applied and published. `World::register_identity_with_cells` then drives its declared observations through assessment, crosses the identity-maintenance and model-owner barriers, and exact-compares the competitive cells in the published dimension map before returning. That is the harness's job — a test that reconstructed the waits for itself would be measuring the scheduler.

Two of the barriers exist because two queues do, and neither covers the other. `World::flush_labels` rides the command channel and its handler drains the label channel before acknowledging, so commands and labels submitted before the call have landed when it returns. Cold-ramp observations ride a third channel, reached only once the command queue has emptied (`dec:concurrency:channel-preemption`) and untouched by the marker's handler; `World::flush_observations` is the barrier for those. A scenario reading the accepted count or the standardisation phase after a flush of labels alone is reading whatever the steward happened to have got through.

Six barriers stand in all, one for every asynchronous queue a test can reach, and the set is closed: nothing reachable is left to a guess or a sleep (`entry:assayer:harness-closed-barriers`) (`dec:harness:no-ad-hoc-waits`). Beside the two above, `World::flush_identity_maintenance` sends the maintenance loop's checkpoint marker and then the publication barrier, so the lifecycle changes that cycle accepted have been applied and published when it returns; `World::flush_ledger_gc` triggers one collection cycle and hands back its merged outcome; `World::flush_checkpoint_scheduler` returns once the scheduler has placed its request on the owner's queue, and deliberately not once that request has been served; and `World::drain_health_events` orders every producer — maintenance, then observations, then commands and labels — before draining the bounded receiver. `World::publish_lifecycle` submits an empty lifecycle batch and crosses the publication barrier, for a scenario that needs a publication without a registration. Every one of them documents what returning covers and what it excludes, because a barrier read as covering a queue it never touches is worse than no barrier at all.

`World::settle_cold_ramp_with` is built on the second barrier. Each request loads the published snapshot for itself (`dec:concurrency:per-request-load`) and an accepted observation advances a later one (`dec:ordering:score-before-evolve`), so two assessments taken while the ramp is transitioning can be answered in coordinate systems one advance apart — the ramp working, not a defect, and the corpus does not promise otherwise (`inv:guarantee:evidence-authority`). The loop offers the scenario's own requests a burst at a time, waits on the observation barrier, then reads the published phase and accepted count. No wall clock takes part: each iteration ends with the queue empty, so the accepted count has strictly risen or the ramp is not moving, and a stall fails with both counts named rather than as a timeout.

Above those sit the ergonomic verbs. `World::derive_on` and `World::derive_default` collapse assess-then-derive; `World::cycle_on`, `World::cycle_default`, `World::cycle_benign` and `World::cycle_adverse` collapse a whole assess-label-flush round; and the free function `cycle_request` does the same for a caller-built request rather than a named channel and entity. Two escape hatches remain deliberately open: `World::assayer` hands back the engine, and `World::shut_down_model_owner_for_test` and `World::block_model_owner_for_test` reach the crate-internal command variants that park or kill the owner thread for failure-surface tests. The blocking form returns a guard whose `Drop` releases the owner.

Reading state back is its own surface with one contract. `testing::probes` holds three owned projections — `PublishedModelBlock`, `PublishedSlotMoments` and `PendingEntryView` — and every `World` entry point returning one crosses the barrier that reading depends on, takes exactly one source view, copies only retained fields, exposes no route back to mutable engine state, and takes any observation time from the scenario's clock (`dec:harness:probe-contract`). The published readings cross `World::flush_labels` and then load one snapshot, so a model block and a slot's moments each carry the version and layout generation they came from; `World::pending_entry_view` crosses nothing, because pending insertion completes on the assessing thread, and performs one non-consuming lookup that keeps the buffer's actual storage width. What the projections omit is as deliberate as what they carry: the working precision matrix is absent and is not to be added (`cav:retention:probe-boundary`), so a witness about precision stays in the crate's own tests, where that state is directly reachable. Two further readings ride the same discipline — `World::observed_runtime_layout` reports published widths without applying the builder's declaration, and `World::sentinel_departing_block_width` measures the coordinate block one removal owns, its slot plus every interaction whose identity names it.

A long stimulus is data rather than a loop. The subject owns its row type and implements `PlaybackRow` — a diagnostic name, and a `play` that applies the row without choosing a barrier — while `testing::playback` owns the semantics around it (`dec:harness:declarative-playback`). A `PlaybackBarrierPolicy` names, in order, which of the six barriers each row boundary crosses. A `PlaybackCheckpoint` is declared for exactly one zero-based row and refuses to be skipped, repeated, or invoked at another boundary, every refusal naming the checkpoint and the row it ran at. `PlaybackProgress` advances once per completed row and reports the first incomplete one, which is liveness evidence and never a latency reading (`cav:harness:progress-not-latency`). `PlaybackBatchSize` bounds how many rows are materialised together, which changes allocation and dispatch cost and no observable boundary, because each row is still applied, settled, checkpointed and counted before the next begins. Failures name their row: `PlaybackError` separates a subject's own refusal, a barrier failure with the barrier named, and a checkpoint violation, and progress stays on the first incomplete row so a stalled run says where it stopped.

Durability is the last World-facing mechanism. `World::fork_persistence` and `World::fork_persistence_after` consume a persistent world and return a `PersistenceFork`: two worlds, one uninterrupted and one rebuilt from a copy of the first's checkpoint and journal, sharing the single scenario clock (`cor:durability:harness-fork`). The copy is taken at a quiescent boundary — identity maintenance, observations, Ledger collection, the checkpoint scheduler and labels, in that order — and with the owner parked, so the durable prefix is fixed rather than sampled while the scheduler works. Only then does the clock move by the caller's elapsed duration, which is what makes the restored arm measure downtime between two scenario readings instead of a wall-clock one. Names and host-owned policies are copied into the restored arm; models, Ledgers and owner state are rebuilt from the durable copy alone. A callback rebinds the process-local identity encoders no checkpoint can carry, and construction refuses a callback that moved the clock or left a registration unbound, because a dropped dimension would quietly shrink the state under comparison. `PersistenceFork::arms` borrows both worlds, `into_arms` hands them over with the storage lifetime that follows them, `roots` names each arm's directories, `advance` moves the one clock and then settles each arm's time-activated work, `journal_bytes` freezes both journals with both owners parked, and `wall` reports what the copy and the rebuild cost.

## Time · `sec:assayer:testing-architecture-clocks`

`Clock` reports both timestamp domains the corpus keeps apart (`dec:clock:two-domains`): `Clock::now` serves the persistent domain and `Clock::now_monotonic` the intra-process one. The separation is the distinct typed readings and the absence of a conversion, not permission for a scenario to skew two notions of the same present. One handle therefore carries both, and `World::advance` and `World::travel_to` move them together by one offset. That pair is the whole of a scenario's control over time (`cor:clock:harness-control`) (`entry:assayer:testing-harness-concept-time-verbs`): it preserves the production relationship between persistent and intra-process events, and it leaves a domain mistake unwritable, because neither reading can stand in for the other.

`SystemClock` is the production implementation and the only piece of the harness that survives into a sealed build. `VirtualClock` is the deterministic one. It stores nanoseconds since the Unix epoch in an atomic so several threads read without locking, holds the reading taken at construction, and expresses the monotonic domain as an offset from a real instant captured once — an `Instant` is opaque and cannot be synthesised, so the virtual monotonic reading is built by addition rather than from an absolute value. Raw backward travel panics, which keeps the low-level monotonic contract unmissable; `World::travel_to` checks first and instead returns `WorldFixtureError::BackwardTimeTravel` with the current and requested persistent instants, before either reading moves. `VirtualClock::advance` saturates at its latest representable reading rather than wrapping backward. `Clock` is implemented for `Arc<VirtualClock>` as well as for the value, which is how one clock is shared between engine and harness.

A clock instance belongs to one `World` and is never a process-wide or thread-local singleton, because integration tests run many worlds in one process and a shared clock would let them observe one another. `WorldBuilder::clock` exists for the cases where sharing is what the scenario means, and `World::clock` exposes the distinct typed readings for guards and witnesses. Scenario movement goes through `World::advance` or `World::travel_to`. After either moves the shared offset, it crosses `World::flush_identity_maintenance`, including accepted lifecycle publication, because monotonic time can make identity decay due; it then crosses `World::flush_ledger_gc` because persistent time can make retained entries collectable. Cold-ramp observations, checkpoint scheduling and health-event draining remain excluded: movement submits no cold-ramp work, the checkpoint scheduler waits on a real interval rather than the virtual clock, and draining events would consume host-visible output rather than settle a producer activated by time. `PersistenceFork::advance` is that movement for a forked pair, advancing the one shared clock through the uninterrupted arm and then settling the restored arm's identity maintenance and Ledger collection, so both arms stand at one present with the work that present made due already done.

## Construction, registration and the name vocabularies · `sec:assayer:testing-architecture-vocabularies`

Some of the construction contract's parameters are host-set with no default, and a construction that never declared one refuses to build (`tab:construction:parameters`). The harness builds instances, so the harness is a host and declares like one (`dec:assayer:harness-declares`). `testing::construction` holds the infrastructure declaration: a command-channel capacity and the `test_infrastructure` function that returns the defaults with that one field filled. `WorldBuilder` holds the scenario declarations, including the required deterministic seed and the interaction templates forwarded to engine validation; its optional expected layout is checked by `World::runtime_layout` against one published dimension map. `CompetitiveCellSpec` makes an identity fixture state its observation workload, graph budget and exact expected set before `World::register_identity_with_cells` begins. The construction figure and its reason are registered (`tab:assayer:harness-construction-figures`), and the harness mints a constant head and a form pin for it rather than leaving a literal standing.

A declaration is worth having only if something checks it, so every construction fixture measures what it built. `WorldConstructionBaseline` is that measurement — instance id, generator state, persistent clock reading, every published block width, publication version and layout generation, the complete channel declarations in assignment order, the lifecycle populations, the ramp's phase and accepted count, and the label and assessment counts — and `WorldConstructionDeclaration` pairs the exact baseline expected at construction with the optional layout the scenario says it will grow into. `ConstructionFixture` names the five constructors that apply the guard — `WorldBuilder::build` when it carries an expected layout, `World::cold`, and the three scenario constructors — and `ConstructionFixture::guard_baseline` refuses with the whole declaration and the whole measurement beside it, so a diagnostic says which fact differed rather than that something did (`dec:harness:guarded-fixtures`). `ChannelBaseline` and `ChannelPolicyBaseline` make the channel half of that exact: every reward and posture scalar is compared by its bits, because a policy that arrived slightly wrong is not the policy the scenario declared.

`testing::fixtures` carries the one shared state-establishing fixture. `World::trained_state` builds the score-verified training population and returns a `TrainedStateFixture` — the world, and the baseline that admitted it — only after measuring both training class counts, the held-out endpoint gap and the tie-corrected pairwise rank over twenty examples per class, and it refuses with every measured value when a count differs or a floor is not exceeded; the four figures and their reasons are registered (`tab:assayer:harness-trained-state-fixture-figures`). That guard ends at the setup boundary and says nothing about the result: a fixture establishes that the subject is ready for a test, while an oracle separately decides whether the code under test produced the promised answer, and one check doing both would report a result disagreement as broken setup (`dec:harness:separate-validation`).

`testing::registrations` builds the three lifecycle payloads crate tests submit directly — `sentinel_reg`, `axis_reg` and `spatial_axis_reg` — with generated names and a fixed initial precision and decay, so the same shapes do not drift across files. `testing::dimensions` sits one layer below the `World` harness and builds the raw index and vector shapes the feature-layout rebuild expects: `sentinels`, `dims`, `cells`, `axes`, `n_axes` and `make_cells`. A slot's outcome-memory pairs are laid out in the order the axes arrive, so a fixture naming them names their positions too, and `n_axes` exists for the fixtures that care only how many pairs the slot tail carries.

`testing::names` replaces raw integers everywhere in the scenario vocabulary. `SentinelName`, `AxisName`, `ChannelName` and `IdentityName` are transparent wrappers over `&'static str`, each with a `From` impl so a call site writes a string literal. `NameRegistry` keeps four registration-ordered vectors and three counters, answers lookups by name, and allocates ids for the callers that do not want a name. A test never handles it: names go in through the lifecycle verbs and ids come back out of them.

## Signals and the specification builders · `sec:assayer:testing-architecture-specs`

`testing::signals` declares the standard request-scoped schema — one clipped scalar named `score` and one binary named `verified` — and the payload functions that attach it. The pair is deliberately tiny: enough to exercise request-signal assembly without every test declaring ad-hoc boilerplate. `with_score_verified` takes explicit values; `with_standard_training_score_verified` varies them by cycle so a stream is non-constant yet identical across matched worlds; `with_standard_final_score_verified` fixes the final reading. `with_degraded_score_verified` is the deliberate fault: one non-finite numeric value and one shape mismatch, which exercises both public signal-degradation counters at once.

A specification is a fluent builder over a production payload that has many fields because it is a host-facing contract, when a test almost always cares about one knob. Three exist and they share a shape: `new` fills clean defaults, each setter returns `Self`, and `build` yields the production type. The two that wrap a payload a scenario submits, `LabelSpec` and `PreSeedSpec`, also carry named shorthands for the two valences and a `From` impl beside `build`; `DegradationSpec` carries neither, because a degradation context has no common case worth naming.

`LabelSpec` builds `LabelData` and carries one field that is not part of it: an optional challenge outcome, readable through `LabelSpec::challenge_outcome`, which the cycle helpers route to the companion tracker before submitting the core label. `LabelSpec::action_taken` is what those helpers read to decide whether routing applies. `PreSeedSpec` mirrors it for the pre-seed entry surface. `DegradationSpec` covers the seven independent degradation signals of a context that is `#[non_exhaustive]`, including the counter for values the boundary zero-fills rather than rejects (`dec:surface:sanitise-not-reject`).

A test states a stream by handing one of these builders to a cycle verb as a closure keyed on the assessment id the engine has just issued, which is why the label payload can vary per cycle while the ceremony around it stays in one place.

## Reports · `sec:assayer:testing-architecture-reports`

`testing::reports` is the Sentinel-side fixture surface. It declares one routing coordinate whose leading four, eight and twelve bits are three cells' lower bounds, three cell lower bounds derived from it, and a nested `scores` module holding a peak z-score array and an accumulator array for each depth. Those readings are stimulus the harness authors and never output it recorded (`dec:assayer:golden-report-stimulus`): nothing computes them and no procedure in the package would reproduce them. Their shape is discrimination — the ladder rises with depth on three axes while surprise is held flat, so a layout that reads the right number from the wrong slot shows up as a number where zero belongs — and each figure is registered with its reason (`tab:assayer:harness-golden-figures`).

Above the constants sit the builders. `make_cell_report` assembles one cell, computing the exclusive interval end from the depth and treating depth zero as the whole space. `default_health`, `default_contour` and `default_analysis_set_summary` supply the report-level metadata. On top of those, eight whole-report fixtures: `golden_report` at depths zero, four and eight; `golden_report_4cell` adding a depth-twelve cell for the four-cell acceptance criterion; `minimal_report` with the root alone; `degraded_report` with a non-finite peak in one cell; `report_missing_root`, `report_with_duplicates` and `report_non_dyadic` for the three structural rejections; and `report_many_cells` at a hundred cells. Six single-cell builders — `make_test_cell`, `make_nan_cell`, `make_inf_cusum_cell`, `make_negative_variance_cell`, `make_high_noise_cell`, `make_negative_noise_cell` — cover the per-cell faults, and `make_coordination_report` builds the coordination shape.

Two helpers close the loop back to the `World`. `refresh_golden_report` ingests the canonical report for an already-registered Sentinel and asserts the acknowledgement's cell count and clean degradation; `attach_golden_reporting_sentinel` registers the Sentinel, crosses the publication barrier and then refreshes, returning the id.

`testing::performance` composes those reports with `World`, `LabelSpec`, `PreSeedSpec` and the existing `VirtualClock` into six declared real-engine cases whose dimensions, counts, mixes, completion and health are guarded before a measurement can begin. `PERFORMANCE_CASES` is the single declaration of those six workloads, and each guard — fixed clock origin, absent persistence, the channel's declared action set, the population mix, the synthetic reports' acknowledgement, clean health, the model-row count, pre-seed completion, the reference removal — refuses with what it measured, so a benchmark cannot quietly measure a population it did not get (`dec:harness:performance-benchmarks`).

The `performance` Criterion target is a consumer outside those three test surfaces and reaches `torrust_assayer::testing::performance` through the package's self dev-dependency with `test-support` enabled. It maintains the `assessment`, `label_publication`, `construction_shutdown`, `pre_seed`, `health` and `reference_marginalisation` groups; their registered functions are (`test:bench:bench-assessment`), (`test:bench:bench-label-publication`), (`test:bench:bench-construction-shutdown`), (`test:bench:bench-pre-seed`), (`test:bench:bench-health-summary`), (`test:bench:bench-full-health-report`) and (`test:bench:bench-reference-marginalisation`).

The `Benchmarks` workflow runs that target weekly and on manual dispatch with explicit comparison settings, isolated stable and nightly target directories, recorded runner and fixture context, and a bounded complete-report artifact; its delivery status is (`entry:assayer:performance-ci-route`).

## Assertions, tolerances and drift budgets · `sec:assayer:testing-architecture-assertions`

`testing::asserts` is a flat set of `#[track_caller]` functions rather than a builder. The primitives are `assert_near`, `assert_below`, `assert_positive`, `assert_in_unit_interval` and `assert_finite`; every failure message names the label the caller passed, so a stack of assessments inside a churn loop can be told apart at a glance. Above them sit the domain readers, which take a `DerivedReckoning` and pull one payload out of it: the risk basis, the outcome-prediction map, one named axis's prediction, the per-Sentinel alarm summaries, the inline health snapshot, the resonance profile, and the two combinations — the whole public core payload, and that payload together with the profile. All but the risk-basis reader come in pairs, a default form applying `PURITY_DRIFT` and a `_with_drift` form taking a budget, which is how a comparison with an independently justified allowance stays legible as such; the risk-basis reader has no pair because a caller wanting its own width states it through `assert_risk_basis_near` over the two bases. Three readers choose no budget at all: `assert_reckoning_well_formed` checks one reckoning's shape, `find_tag` names a missing tag kind instead of panicking on an index, and `assert_signal_degradation_counts` states an expected degradation footprint exactly.

Two assertions are structural rather than numerical. `assert_tag_profile_near` compares count, order, tag kind and domination flag exactly and the three floating-point payloads within a tolerance. Its liveness counterpart `assert_tag_profile_diverges_somewhere` requires the two profiles to agree on length and kinds and to differ past an epsilon in at least one triple, which is what stops a regression that silently neutralised a perturbation from passing as agreement. `assert_health_clean` reads the engine's health summary and fails on any per-assessment degradation counter or hard-failure flag, while deliberately admitting the detection and observability signals that report and never act (`inv:monitoring:report-only`), the convergence and calibration fields a fresh world legitimately sits in, and the cold ramp's own refusal trace, which is reported in band (`cor:degradation:in-band-travel`) and must still account for every degraded assessment. It also fails on a dropped health event, because an event the bounded receiver refused is a reading no later drain can recover.

`testing::tolerances` centralises the epsilons so a scenario says "near" and the harness chooses the bound. The bundle's eight fields do not all have the same standing, and the table that declares them says which each has (`tab:assayer:harness-scenario-tolerances`): two are figures the specification states, one is the harness's reading of a specification that gives a condition rather than a ceiling, four are the harness's own, and one is exact equality rather than a tolerance at all. One field is a coefficient rather than a bound: the specification states the synchronisation threshold as a coefficient times the dimension (`def:monitoring:synchronisation-error`), so callers take the ceiling from `Tolerances::precision_sync_ceiling` at their own model width and no width is admitted more departure than the specification would admit it. Every field is read by at least one assertion, which is what keeps the bundle a vocabulary rather than a collection (`cav:assayer:harness-unconsumed-tolerances`).

`testing::drift` holds three budgets for comparisons that necessarily evaluate independent engine paths. `PURITY_DRIFT` answers identical-input and request-order replays across those paths; `LIFECYCLE_SUFFICIENCY_DRIFT` and `DIVERGENT_OUTCOME_REPLAY_DRIFT` serve the longer lifecycle and nonlinear resonance paths. A budget is not used to prove that an assessment field is excluded from derivation when the arithmetic inputs can instead be held fixed: the live-outcome-prediction witness clones one completed assessment, clears only its prediction payload, derives both forms through the same policy and Companion state, and requires exact agreement. Because both calls read the same held risk basis, training-time reduction association cannot enter that comparison and any prediction dependence fails at zero tolerance.

`testing::oracles` answers a different question from an assertion: not whether two engine paths agree with each other, but whether the engine agrees with an independently computed reference (`dec:harness:oracle-tier`). Four routes stand there, each declaring its provenance through `OracleProvenance` and a constant beside the function, and all four declare `SpecificationFormula` — a formula the specification states rather than a reference the harness chose. Each is deliberately written against the production route it checks: `pairwise_rank` enumerates positive-against-negative pairs with a tie credit instead of sorting and summing ranks; `regularised_schur_complement` solves one dense augmented system by partial pivoting instead of taking the Cholesky half-solve; `decay_recurrence` multiplies label steps and whole hours one at a time and evaluates only a residual fraction in logarithmic form instead of calling a power; and `dimension_width` forms every block term of the layout formula independently instead of walking a shared cursor. An oracle that reimplemented the production route would agree with it for the wrong reason, which is the one failure the tier exists to exclude (`cav:harness:oracle-trust`).

`testing::sweeps` is the property envelope, and it is framework-free by construction. `run_seeded_sweep` takes a declared seed, a case count, a draw and a witness, and reports a rejection with the seed, the zero-based case index, the complete drawn input and the witness's own reason. The seed is mandatory because the generator has no default, and there is no shrinking and no hidden entropy to move a failure away from the stream that produced it (`dec:harness:seeded-sweeps`). A drawn case's `Debug` rendering is the replay format, which is why a case type carries every generated value its witness consumes rather than a summary of them.

The persistence fork's own comparison is `DurableProjection`, crate-internal for the same reason the probes exclude precision. It projects the whole checkpoint payload into an owned, field-addressable value through `DurableValue`, a serializer that keeps map keys of any shape, preserves sequence order, and renders a non-finite float as its bits rather than as a null. The projection destructures the payload exhaustively, so a new durable field is a compile-time refusal until it has an explicit projection rather than a silent absence from every comparison. The field groups whose order comes from hash maps are sorted by their own identity; the capture timestamp is nulled, because it dates the act of checkpointing and not the state; and the sequence marks stay exact, because resetting one would hide a lost or duplicated label. `DurableProjection::compare` answers with the first difference addressed by field path, and its numeric comparison admits sixty-four units in the last place scaled to the compared magnitude — the rounding two legitimate arithmetic orderings can differ by, and far below a second decay factor (`dec:harness:probe-contract`).

## Liveness · `sec:assayer:testing-architecture-liveness`

Every wait an integration test takes on the label path is unbounded. A flush blocks on an acknowledgement with no timeout, which is the right shape for the engine — a host wants the barrier, not a partial one — but it means a model owner that stops answering leaves the test thread parked in a wait its own loop conditions are never reached from, and the test then reports nothing at all: no assertion fails, no message is printed, and the run ends when whatever is running it gives up. The other barriers are bounded: identity maintenance, Ledger collection, the checkpoint scheduler and the parked-owner handshake all wait under `ACK_DEADLINE` and fail with a diagnostic naming the queue, so the unbounded wait is now the label path's alone.

`testing::liveness` turns that into a failure three ways. `fail_fast_on_model_owner_panic` installs a panic hook that runs the previous hook first, so the owner's own message and location print exactly as they would have, and then ends the process with the failing-test exit status only when the panicking thread's name carries the owner marker — every other thread's panic unwinds normally, so an ordinary failed assertion and a `should_panic` test are untouched. `watch_progress` returns a shared counter and spawns a watcher that prints where the harness has got to every heartbeat, so a run killed from outside still carries its own trail, and ends the process when the counter has not moved for the stall bound; `advanced` and `finished` are the two verbs a driving loop calls. The stall bound is deliberately not a bound on the run: a schedule that legitimately takes a long time is allowed to, and what is never legitimate is one that stops advancing and stays that way. Both are opt-in per test binary and neither is armed by including the module.

`ACK_DEADLINE` and `STATE_DEADLINE` are the third thing and are not opt-in: they are the deadline every bounded acknowledgement wait in the harness and in the crate's own tests is written against. The two are equal, the second defined in terms of the first so they cannot drift apart by accident, and they carry separate names because the call sites read better for it. They are generous rather than tight, and the reason is that they answer a liveness question and never a latency one. The harness sends a command, a loop answers it, and the only thing the wait decides is whether the loop is still answering at all; no test asserts anything about how long the answer took, and a test that wanted to say the answer arrives quickly would have to say so itself with its own assertion on elapsed time. A deadline is not a budget — the wait it bounds is the same wait either way, and it expires only when the answer is never coming — so nothing is bought by failing sooner, while an instrumented coverage build of this crate runs about a hundred times slower and a deadline sized for an ordinary run would fabricate a failure there and leave the suite unmeasurable. A hung loop still fails; it fails later.

## The maintenance harness and the source scanner · `sec:assayer:testing-architecture-side-harnesses`

Two modules serve subjects the `World` does not reach.

`testing::maintenance` drives the crate's internal identity-maintenance thread directly (`dec:harness:specialised-side-harnesses`). `MaintenanceHarness` owns the spawned thread and both channels, and its `Drop` sends the shutdown command and joins, so a test never leaks a thread on panic. It declares its own model-owner channel depth, wide rather than derived, so a test draining the receiver after the loop has run never blocks the maintenance thread against it; the figure has no counterpart in a deployment, which is why the harness declares it (`tab:assayer:harness-construction-figures`). Around that sits the vocabulary: two Mudlark configurations, `setup_dimension` for a matching pair of dimension infrastructure and observation channel, two registration verbs that wait for the acknowledgement and one fire-and-forget destruction, `flush_identity_maintenance` for the seam's own barrier, two verbs that drain or discard the emitted commands, `shutdown` for an explicit join, a free function that flattens lifecycle events out of a batch of commands, and the raw command sender for the low-level cases the vocabulary does not wrap. One method, `force_decay`, is itself `#[cfg(test)]`, because the command variant it sends is.

Its three constructors are guarded as the world's are. `MaintenanceFixture` names them — `setup_dimension`, `MaintenanceHarness::spawn` and `MaintenanceHarness::spawn_with_capacity` — and each derives a `MaintenanceFixtureDeclaration` before it builds anything and reads the result back afterwards: the dimension fixture reports the identifier, name, descriptions, domain width, cutoff, encoder probes over an empty and a non-empty key, the published and tracked cells, the published importance by its bits, the dropped and active-indicator counts, the graph snapshot, and both views of the observation queue including capacity, occupancy and overflow; the harness fixtures report thread presence, liveness and name, and both queues' capacity and occupancy. A mismatch refuses with the whole declaration beside the whole measurement. The seam's barrier and the world's share a name and cover different work: the marker here drains the registered observation queues and the deferred signal-cache writes, detects competitive-set changes, offers their lifecycle submissions and publishes graph snapshots, while nothing in this harness runs a model owner that could apply them, so a test needing that composition uses `World::flush_identity_maintenance` instead. The module carries that whole reachable-queue inventory in its own documentation, at the fixpoint where no reachable queue is left uncovered (`entry:assayer:harness-closed-barriers`).

`testing::source_scan` factors the shape every repository-hygiene audit shares: walk the source tree, open every Rust file, inspect each line. `SourceTreeScanner` is a builder with directory and file skips and a per-line visitor; `LineVisit` carries the path, the one-based line number, the line and a coarse flag saying whether a test attribute has been seen earlier in the file. The root comes from `manifest_dir`, which reads the manifest directory from the environment at run time rather than baking it at compile time. That distinction is the module's substance: a source audit asks a question about the tree it is being run against, and the compile-time value names whichever checkout produced the binary — a different tree the moment a build cache is shared between clones, in which case the walk would audit somebody else's source while reporting on this one. The compile-time value survives only as the fallback for a binary invoked outside cargo.

## The multi-channel support tree · `sec:assayer:testing-architecture-multi-channel`

The support tree is private to the `multi_channel` binary and compiled once. It is a module tree rather than a set of path includes, which is what makes an item that loses its last caller a finding rather than something a blanket allowance would cover. Its own module documentation says so, and the repository's clippy discipline is the rule behind it (`[INDEX-sec:index:agents-clippy-exception-discipline]`).

Its subject is one seam: what a channel is for cannot bend what the engine believes about the entity behind it. Everything in the tree is scaffolding for probing that seam across many shapes at once, and it layers.

`support::constants` holds three canonical action sets and the three tag sequences they should produce. `support::policy` builds channel policies from an action set, from an action set and a reward block, or from an action set and a perturbation applied to the default rewards; the perturbation form is the shape the whole tree is built around, where two channels share an action set and one changes exactly one decision-layer knob.

`support::rewards` turns that into data. A perturbation case names itself, carries a stable seed salt, an action set, the expected tags and a function pointer that mutates one reward field; nine of them stand in a sweep covering the reward axes one at a time. Two scenario builders declare a baseline channel and a perturbed one, and a single assertion drives one named case end to end.

`support::labels` states observation streams as data. A label-cycle case is entity, action, valence sign, ground-truth flag and an optional challenge outcome, with a method converting it to a `LabelSpec`; a pair holds two such cases for the probes where two worlds should see the same stream but one deliberate difference. Stream constructors produce alternating entity or alternating valence sequences. The driving verbs run one case, a stream of cases, a matched pair across two worlds, or a matched stream — and the matched-stream verb settles both worlds' cold ramps before their histories diverge, because two worlds trained in parallel otherwise reach different accepted counts for no reason but scheduling.

`support::outcomes` trains outcome-axis predictions through ordinary public labels rather than by reaching into model state, in single-world and matched-pair forms, with canonical values and a canonical cycle count. It adds two assertions the library harness has no place for: that every reckoning in a list carries the same prediction, and that two predictions are ordered by raw value with a minimum gap.

`support::assertions` is the tag-level vocabulary. It partitions a profile into action tags and classification tags, counts and sums them, and asserts an exact action-tag sequence. A core-payload expectation bundles the three liveness witnesses — a live reporting Sentinel, a live outcome prediction, an expected signal-degradation footprint — behind constructors that name the combination. The composite assertion states the independence shape in full: the core assessment is fixed, classification tags are fixed, and the action tags must diverge somewhere, with classification asserted separately so the liveness check lands on the action tags rather than being satisfied by an unintended core-side movement.

`support::derivation` holds the matrices and is the second-largest module in the tree. A derivation case is a channel name and its expected action tags; a matrix bundles an ordered case list with the same-action pairs whose action layer must move, so a call site cannot pair one matrix's cases with another's liveness assertions; a request-order matrix adds the reordered case list. Three standard matrices stand as constants — the three-channel independence fixture, the four-channel policy matrix, and the challenge-and-reward matrix — each with its reversed twin. Above them sit the scenario builders and forty-three assertion and fixture functions covering same-batch fixed-core comparisons, request-order replays, cross-world batch replays, and the two things a replay may be compared on: the full public core assessment plus the profile, or the sufficient risk statistic plus the profile.

`support::enrichment` is the tree's largest module and crosses all of that with the request shapes the public surface admits. An enrichment is a name, a signal mode of three values, a reported-Sentinel flag, a live-outcome flag and a seed salt; twelve of them form the grid, and the outcome-bearing half is addressable separately. An enrichment knows how to decorate a request for training and for the final assessment, whether the world needs a signal schema, which Sentinel and axis to register, what core payload to expect, which drift budget and which replay comparison its payload warrants, and which health assertion applies — the degraded variants get their own, since a deliberately degraded stream must record sanitised signals while leaving every other degradation counter at zero. Core history is a third axis: a fresh world, a world moved by an alternating label stream, or one moved by an identity dimension plus that stream. The family runners compose the three: for each point in the grid, build a world, prepare the history, train any decision-layer evidence, replay the matrix, assert health. The alternating label history is itself a playback — the tree owns a row type and hands it to the library runner under a bounded batch size — so even the longest stimulus here is driven by the shared semantics rather than a private loop (`dec:harness:declarative-playback`).

What it duplicates from the library harness is small and deliberate. The `_with_drift` pairing is the same discipline. `support::labels` re-derives the challenge-routing step that `World::cycle_on` and `cycle_request` already perform, because its paired verb drives two worlds and cannot delegate to either. `support::assertions` and `support::outcomes` wrap library assertions rather than reimplementing them — the classification-tag comparison is the library's tag-profile comparison applied to a filtered slice. What it specialises is everything else: the grid, the matrices, the reward sweep, the channel vocabulary, and the paired-world ceremony, none of which any other binary runs.

## The label vocabulary · `sec:assayer:testing-architecture-labels`

Harness mechanisms mint no behavioural claim or test. A reader tracing another helper to its callers still does so through the generated per-file indexes rather than through a citation.

Each tree mints a generated folder matrix. The library-harness matrix now projects the playback scheduler witnesses, while the private multi-channel support matrix remains empty because that tree supplies specialised scaffolding rather than standalone tests.

What the harness mints beyond that is figures. ## Observations · `sec:assayer:testing-architecture-observations`

**Observation (The feature comment understates the harness caller surfaces)** · `obs:assayer:testing-architecture-three-surfaces`

The manifest's feature comment calls the gated surface the integration-test surface, and the gate comment in the library root names crate tests and integration tests, while the module's own header names four consumers: inline tests, crate tests, integration targets and benchmarks. Thirteen production source files carry inline test modules that name `crate::testing` directly, and the Criterion target reaches the flattened surface through the self dev-dependency. Nothing is wrong with the compile arrangement — the crate's own test build admits an inline module and the self dev-dependency admits every target — but both comments still understate the caller boundary a retirement census has to search.

**Observation (The caller census closes unreported public harness decay)** · `obs:assayer:testing-architecture-unreported-decay`

The flattened test-support surface is public, so dead-code analysis alone cannot report a helper whose external callers disappear. The moved-base census therefore searched inline, crate, integration, benchmark, and harness callers together. It retained the clock-travel chain and the model-owner guard's explicit release because live scenarios call them, removed every residual callerless entry point and its supporting state, and stopped flattening the tracing initializer that only the scenario constructors use. The module documentation now states this census boundary instead of promising a compiler diagnostic the public surface cannot provide. The retirement that ran that census is recorded as complete, which discharges the finding without retiring its reason: the surface is still public, so the next retirement still owes a census rather than a diagnostic (`entry:assayer:harness-stale-helper-retirement`).

**Observation (The deadlines are liveness numbers and not latency budgets)** · `obs:assayer:testing-architecture-deadlines-are-liveness`

`ACK_DEADLINE` and `STATE_DEADLINE` are five minutes, which reads as an extraordinary latency allowance and is not one. Nothing in the suite asserts that an acknowledgement arrives within them; they exist so that a loop that has stopped answering makes its own test fail with a message naming the wait, instead of parking the test thread until the runner gives up on the whole run. Sizing them down would buy nothing, because the wait they bound is the same wait either way, and would cost the coverage job, whose instrumented build runs about a hundred times slower than an ordinary one. A test that wants to say something about how quickly an answer arrives has to assert on elapsed time itself.

**Observation (The synchronisation target imports the common liveness contract)** · `obs:assayer:testing-architecture-liveness-copy`

Commit `edd8582d9` replaced the synchronisation-drift target's copied failure status, owner-thread marker, progress type, panic hook, watcher, and counter verbs with imports from `testing::liveness`. The target now shares the same failure messages, branch order, deadlines, and progress semantics as the other liveness consumers, discharging the copy recorded here.

**Observation (Harness prose now describes the roster that exists)** · `obs:assayer:testing-architecture-staging-notes`

The harness and world module headers once carried a stage narrative, which left a reader unable to tell a callable surface from a planned one. They now describe present construction, scenario-time, barrier, fixture, probe, playback, oracle, sweep and assertion capabilities; the verb table names only callable world operations, the report header lists only defined fixtures, and the architecture and implementation rosters transcribe the declared modules and their flattened exports. The retirement that rewrote those headers discharges the finding, and future work stays in its owning backlog entry rather than appearing as a promise in module documentation (`entry:assayer:harness-stale-helper-retirement`).

**Observation (Only the support tree's matrix still marks a folder as scaffolding)** · `obs:assayer:testing-architecture-empty-matrices`

A generated matrix reporting no tests was the only structural marker distinguishing a scaffolding folder from a test folder: nothing declares a folder to be scaffolding, so a reader had to infer it from the emptiness. Half of that has since changed. The library harness folder's matrix now projects the playback scheduler's seven witnesses, because that scheduler is reachable no other way, so the inference is available only in the support tree and a reader of the library folder cannot make it at all. The other direction holds in both folders: the matrix is computed and compared against the committed bytes on every run, so a test placed in either folder by accident is caught by the mismatch.

**Observation (One maintenance verb is reachable from crate tests only)** · `obs:assayer:testing-architecture-crate-only-verb`

`MaintenanceHarness::force_decay` carries a `#[cfg(test)]` of its own, because the maintenance command it sends is itself test-only. The attribute is satisfied by the crate's own test build and not by the `test-support` feature, so the four call sites are all in the crate test tree and an integration target cannot reach the method however the feature is set. It is the only verb whose availability differs between the two gates. The durable projection and its serializer differ the same way and for the same reason, but they are whole modules rather than one method on a shared type, and their gate names `serde` as well.

**Observation (The paired-world verb re-derives the challenge-routing step)** · `obs:assayer:testing-architecture-routing-duplication`

The decision to route a challenge outcome to the companion tracker before submitting the core label — read the specification's action, read its optional outcome, record it if both are present — is written four times: once in `World::cycle_on`, once in `cycle_request`, and twice in `cycle_request_pair`, which drives two worlds and so cannot delegate to either single-world verb. The four copies agree. The duplication follows from the shape of the paired verb rather than from oversight, and it is the only substantive logic the support tree restates from the library harness.

**Observation (What the intents still ask of the harness is mostly owned readings)** · `obs:assayer:testing-architecture-intent-demand`

The package carries forty-four intent plans, each ending in a section that names what its witness still lacks, and together those sections carry a hundred and fourteen entries. Twenty-seven name a surface this harness does not have. Eight name production code or a ruling the corpus has not made. The remaining seventy-nine are test-local — a subject-owned playback row, a target-local fixture, an integration witness — and ask the harness for nothing at all, which is the ordinary shape of a demand on a harness that is finished: the scaffolding is in place and what is missing is the tests.

The twenty-seven group by mechanism, and the grouping is lopsided. Thirteen ask for an owned reading the present projections do not supply: an entity-bound decay projection, one decayed Ledger cell, Sentinel-slot ranges on the published model block, competitive-cell chains on the pending-entry view, a relocation projection, the shared-subspace blend components, the channel posterior, a joined label route with its post-label state, per-model assessment-time predictors, cumulative leverage-binding counts, the cap values one admitted operational update consumed, and a named Sentinel's mean and covariance sub-block. All but one would land in `testing::probes` behind a `World` entry point; the exception is a read-only channel-posterior reader, which belongs on `World` itself. Three of the thirteen also ask the production label path to publish a value it already computes, and a fourth depends on a production retention change its own plan enters separately, so this group is not purely harness work.

Six ask for a guarded fixture or population: four in `testing::fixtures` — a matched alarming-and-normalised report pair, a dense-conditioning growth fixture, a trained Sentinel pair that survives one retirement, and a sparse-reporting interaction fixture — and two in `testing::performance`, an equal-width ill-conditioning pair and the paired cadence-and-cost sampler that reads it. Three ask the persistence fork for more than a clean two-arm split: a crash-tail image builder taking a configuration transformation per arm, a durable comparison an integration target can invoke, and a replayable registration tape so a restored arm is rebound through the ordinary lifecycle verbs instead of raw registrations. One asks `testing::playback` for a multi-world runner entry point that crosses each world's policy in declaration order, because a row that settled its partner itself would take back the cadence the row contract reserves for the runner. Two ask the support tree for an exchangeable challenge-provider fixture and an exhaustive derivation replay comparator. Two ask for a compile-fail runner — a `trybuild` dependency and a target whose checked diagnostic is the assertion — the one kind of witness neither tree has machinery for.

What the intents do not ask for is as informative as what they do. No entry asks for a new queue barrier, deadline, clock verb or seeded-sweep entry point, and several say so in as many words while consuming the ones that exist. No entry asks for a fifth oracle: the plans that name the tier conclude that the four landed routes answer their question and that what remains is test-local arithmetic around them. One entry rejects a proposed addition outright, on the ground that widening the `World` with Companion controls and a health accessor would duplicate a host-owned surface and blur the boundary its own witness exists to keep. One waits on a specification ruling rather than on any harness surface, which is a corpus obligation and not a gap in this record (`obs:assayer:testing-harness-record-audit-six-rulings`).
