# The Assayer's testing architecture · `rep:assayer:testing-architecture`

_What the package's testing scaffolding is, as it stands. Two trees carry it: the library harness under the `testing` module, compiled into the library itself, and a private support tree compiled into the `multi_channel` integration binary alone. This report describes both — how each is reached, what each owns, and what each declares — and stops where the individual tests begin: what a test asserts is written where the test is, and the catalogue that indexes those statements is elsewhere (`reg:assayer:integration-test-catalogue`)._

## How the harness reaches its callers · `sec:assayer:testing-architecture-reach`

The harness lives in the library rather than beside the tests, and three mechanisms put it there.

The first is a feature. `test-support` is off by default and pulls in exactly one dependency, the tracing subscriber a scenario's span is written through. It is what decides the `testing` module's visibility: under `any(test, feature = "test-support")` the module is `pub` and `#[doc(hidden)]`; otherwise it is `pub(crate)`. A host build therefore cannot name the module at all, which is opacity carried structurally rather than by review (`dec:surface:guidance-opacity`).

The second is a self dev-dependency. The package depends on itself by path with `test-support` enabled, so every test build of the crate — unit, crate-level and integration alike — links a library that has the feature on, while a host resolving the package from the registry gets one that does not. Nothing in the test tree has to ask for the feature, and nothing outside the test tree can obtain it by accident.

The third is the gate inside the module. Only `testing::clock` compiles unconditionally, because production reads its time through `Clock` in every build. Every other submodule carries the same `cfg` the visibility does, so a sealed build compiles the clock and nothing else rather than compiling a crate-private harness that no caller can reach. Gating what compiles is what retired the module-wide `dead_code` allowance that a visibility-only gate would still need.

Within the module, four submodules are themselves `pub` — `testing::dimensions`, `testing::maintenance`, `testing::registrations`, `testing::signals` — because callers name the path and not only the item. The remaining sixteen are private and flattened through `pub use`, so a caller writes `testing::World` rather than `testing::world::World`. One type stays behind the boundary: `names::NameRegistry` is `pub(super)`, owned by `World` and never handed out.

Three caller surfaces reach the result, not two. The crate's own test tree holds fifty-one modules and mints under `test:crate:`; the integration tree holds twenty-one test targets and mints under `test:integration:`; and thirteen production source files carry inline test modules that reach `crate::testing` directly and mint under `test:unit:`. Twenty of the twenty-one integration targets use the harness.

## The scenario and the World · `sec:assayer:testing-architecture-scenario`

A scenario is a `World` and a tracing span bound into one value. `Scenario` declares the world first and the span guard second, so Rust's declaration-order drop runs the world's shutdown — which joins the engine's threads — while the span is still open; the span's close event therefore times the whole scenario including shutdown rather than stopping at the last statement of the test body. `Scenario` derefs to `World` in both directions, so a test that opens with one `let` reads afterwards as though it held the world directly.

Three constructors build one. `scenario` takes an instance id and a seed and wraps `World::cold`, which declares a single `"default"` channel under the default policy. `scenario_with` adds a builder closure and supplies the harness's own infrastructure configuration. `scenario_with_config` takes the whole `AssayerConfig` for fixtures that need to tune it. All three install the subscriber through `init_tracing`, whose installation is idempotent: the first scenario in a binary wins and the rest are no-ops.

The `World` owns six things: a real `Assayer` — there are no mocks anywhere in the harness — a `VirtualClock` shared with that engine, a `TestRng`, the `NameRegistry`, a host-side bundle of channel policies with a challenge-effectiveness tracker and an assessment-to-channel map, and a `Tolerances` value. `WorldBuilder` sets every non-default input explicitly and panics when `seed` was not called, because reproducibility is a contract rather than a default. Channel ids are assigned in declaration order starting at zero, and a malformed policy panics at declaration because a host's own well-formedness check is at policy load (`dec:derivation:ordered-actions`).

The lifecycle verbs — registering and deregistering a Sentinel, an outcome axis or an identity dimension — all end on a private `settle`. The engine's registration path is fire-and-forget and the record declines to promise freshness (`cor:concurrency:reader-obligations`), so a scenario that registers and then assesses has no engine-side guarantee that the assessment sees the registration. `settle` obtains one: it sends the checkpoint marker down the first-in-first-out command channel, and the marker is acknowledged only once everything enqueued before it has been applied and published. That is the harness's job — a test that reconstructed the wait for itself would be measuring the scheduler.

Two barriers exist because two queues do, and neither covers the other. `World::flush_labels` rides the command channel and its handler drains the label channel before acknowledging, so commands and labels submitted before the call have landed when it returns. Cold-ramp observations ride a third channel, reached only once the command queue has emptied (`dec:concurrency:channel-preemption`) and untouched by the marker's handler; `World::flush_observations` is the barrier for those. A scenario reading the accepted count or the standardisation phase after a flush of labels alone is reading whatever the steward happened to have got through.

`World::settle_cold_ramp_with` is built on the second barrier. Each request loads the published snapshot for itself (`dec:concurrency:per-request-load`) and an accepted observation advances a later one (`dec:ordering:score-before-evolve`), so two assessments taken while the ramp is transitioning can be answered in coordinate systems one advance apart — the ramp working, not a defect, and the corpus does not promise otherwise (`inv:guarantee:evidence-authority`). The loop offers the scenario's own requests a burst at a time, waits on the observation barrier, then reads the published phase and accepted count. No wall clock takes part: each iteration ends with the queue empty, so the accepted count has strictly risen or the ramp is not moving, and a stall fails with both counts named rather than as a timeout.

Above those sit the ergonomic verbs. `World::derive_on` and `World::derive_default` collapse assess-then-derive; `World::cycle_on`, `World::cycle_default`, `World::cycle_benign` and `World::cycle_adverse` collapse a whole assess-label-flush round; and the free function `cycle_request` does the same for a caller-built request rather than a named channel and entity. Two escape hatches remain deliberately open: `World::assayer` hands back the engine, and `World::shut_down_model_owner_for_test` and `World::block_model_owner_for_test` reach the crate-internal command variants that park or kill the owner thread for failure-surface tests. The blocking form returns a guard whose `Drop` releases the owner.

## Time · `sec:assayer:testing-architecture-clocks`

`Clock` reports both timestamp domains the corpus keeps apart (`dec:clock:two-domains`): `Clock::now` serves the persistent domain and `Clock::now_monotonic` the intra-process one. One handle carries both, so time travel moves them together while the types stay separated and no conversion between them exists. The monotonic reading is what report staleness and model-decay intervals are measured against, which makes it and not the persistent reading the source of cross-run divergence in reported-Sentinel comparisons.

`SystemClock` is the production implementation and the only piece of the harness that survives into a sealed build. `VirtualClock` is the deterministic one. It stores nanoseconds since the Unix epoch in an atomic so several threads read without locking, holds the reading taken at construction, and expresses the monotonic domain as an offset from a real instant captured once — an `Instant` is opaque and cannot be synthesised, so the virtual monotonic reading is built by addition rather than from an absolute value. Backward travel panics, which makes the monotonic contract unmissable. `Clock` is implemented for `Arc<VirtualClock>` as well as for the value, which is how one clock is shared between engine and harness.

A clock instance belongs to one `World` and is never a process-wide or thread-local singleton, because integration tests run many worlds in one process and a shared clock would let them observe one another. `WorldBuilder::clock` exists for the cases where sharing is what the scenario means. A test governs time through `World::clock`, which hands back the shared handle; `VirtualClock::advance` is the verb tests use.

## Construction, registration and the name vocabularies · `sec:assayer:testing-architecture-vocabularies`

Some of the construction contract's parameters are host-set with no default, and a construction that never declared one refuses to build (`tab:construction:parameters`). The harness builds instances, so the harness is a host and declares like one (`dec:assayer:harness-declares`). `testing::construction` holds that declaration: a command-channel capacity and the `test_infrastructure` function that returns the defaults with that one field filled. The figure and its reason are registered (`tab:assayer:harness-construction-figures`), and the harness mints a constant head and a form pin for it rather than leaving a literal standing.

`testing::registrations` builds the three lifecycle payloads crate tests submit directly — `sentinel_reg`, `axis_reg` and `spatial_axis_reg` — with generated names and a fixed initial precision and decay, so the same shapes do not drift across files. `testing::dimensions` sits one layer below the `World` harness and builds the raw index and vector shapes the feature-layout rebuild expects: `sentinels`, `dims`, `cells`, `axes`, `n_axes` and `make_cells`. A slot's outcome-memory pairs are laid out in the order the axes arrive, so a fixture naming them names their positions too, and `n_axes` exists for the fixtures that care only how many pairs the slot tail carries.

`testing::names` replaces raw integers everywhere in the scenario vocabulary. `SentinelName`, `AxisName`, `ChannelName` and `IdentityName` are transparent wrappers over `&'static str`, each with a `From` impl so a call site writes a string literal. `NameRegistry` keeps four registration-ordered vectors and three counters, answers lookups by name, and allocates ids for the callers that do not want a name. It is the one part of the world a test cannot reach.

## Signals and the specification builders · `sec:assayer:testing-architecture-specs`

`testing::signals` declares the standard request-scoped schema — one clipped scalar named `score` and one binary named `verified` — and the payload functions that attach it. The pair is deliberately tiny: enough to exercise request-signal assembly without every test declaring ad-hoc boilerplate. `with_score_verified` takes explicit values; `with_standard_training_score_verified` varies them by cycle so a stream is non-constant yet identical across matched worlds; `with_standard_final_score_verified` fixes the final reading. `with_degraded_score_verified` is the deliberate fault: one non-finite numeric value and one shape mismatch, which exercises both public signal-degradation counters at once.

A specification is a fluent builder over a production payload that has many fields because it is a host-facing contract, when a test almost always cares about one knob. Three exist and they share a shape: `new` fills clean defaults, named shorthands set the common value, each setter returns `Self`, and `build` yields the production type, with a `From` impl beside it.

`LabelSpec` builds `LabelData` and carries one field that is not part of it: an optional challenge outcome, readable through `LabelSpec::challenge_outcome`, which the cycle helpers route to the companion tracker before submitting the core label. `LabelSpec::action_taken` is what those helpers read to decide whether routing applies. `PreSeedSpec` mirrors it for the pre-seed entry surface. `DegradationSpec` covers the seven independent degradation signals of a context that is `#[non_exhaustive]`, including the counter for values the boundary zero-fills rather than rejects (`dec:surface:sanitise-not-reject`).

A test states a stream by handing one of these builders to a cycle verb as a closure keyed on the assessment id the engine has just issued, which is why the label payload can vary per cycle while the ceremony around it stays in one place.

## Reports · `sec:assayer:testing-architecture-reports`

`testing::reports` is the Sentinel-side fixture surface. It declares one routing coordinate whose leading four, eight and twelve bits are three cells' lower bounds, three cell lower bounds derived from it, and a nested `scores` module holding a peak z-score array and an accumulator array for each depth. Those readings are stimulus the harness authors and never output it recorded (`dec:assayer:golden-report-stimulus`): nothing computes them and no procedure in the package would reproduce them. Their shape is discrimination — the ladder rises with depth on three axes while surprise is held flat, so a layout that reads the right number from the wrong slot shows up as a number where zero belongs — and each figure is registered with its reason (`tab:assayer:harness-golden-figures`).

Above the constants sit the builders. `make_cell_report` assembles one cell, computing the exclusive interval end from the depth and treating depth zero as the whole space. `default_health`, `default_contour` and `default_analysis_set_summary` supply the report-level metadata. On top of those, eight whole-report fixtures: `golden_report` at depths zero, four and eight; `golden_report_4cell` adding a depth-twelve cell for the four-cell acceptance criterion; `minimal_report` with the root alone; `degraded_report` with a non-finite peak in one cell; `report_missing_root`, `report_with_duplicates` and `report_non_dyadic` for the three structural rejections; and `report_many_cells` at a hundred cells. Six single-cell builders — `make_test_cell`, `make_nan_cell`, `make_inf_cusum_cell`, `make_negative_variance_cell`, `make_high_noise_cell`, `make_negative_noise_cell` — cover the per-cell faults, and `make_coordination_report` builds the coordination shape.

Two helpers close the loop back to the `World`. `refresh_golden_report` ingests the canonical report for an already-registered Sentinel and asserts the acknowledgement's cell count and clean degradation; `attach_golden_reporting_sentinel` registers the Sentinel, crosses the publication barrier and then refreshes, returning the id.

## Assertions, tolerances and drift budgets · `sec:assayer:testing-architecture-assertions`

`testing::asserts` is a flat set of `#[track_caller]` functions rather than a builder. The primitives are `assert_near`, `assert_below`, `assert_positive`, `assert_in_unit_interval` and `assert_finite`; every failure message names the label the caller passed, so a stack of assessments inside a churn loop can be told apart at a glance. Above them sit the domain readers, which take a `DerivedReckoning` and pull one payload out of it: the risk basis, the outcome-prediction map, the per-Sentinel alarm summaries, the inline health snapshot, the resonance profile, and the two combinations. Each comes in a pair — a default form that applies a drift budget and a `_with_drift` form that takes one — which is how a comparison with an independently justified allowance stays legible as such.

Two assertions are structural rather than numerical. `assert_tag_profile_near` compares count, order, tag kind and domination flag exactly and the three floating-point payloads within a tolerance. Its liveness counterpart `assert_tag_profile_diverges_somewhere` requires the two profiles to agree on length and kinds and to differ past an epsilon in at least one triple, which is what stops a regression that silently neutralised a perturbation from passing as agreement. `assert_health_clean` reads the engine's health summary and fails on any per-assessment degradation counter or hard-failure flag, while deliberately admitting the detection and observability signals that report and never act (`inv:monitoring:report-only`), the convergence and calibration fields a fresh world legitimately sits in, and the cold ramp's own refusal trace, which is reported in band (`cor:degradation:in-band-travel`) and must still account for every degraded assessment.

`testing::tolerances` centralises the epsilons so a scenario says "near" and the harness chooses the bound. The bundle's eight fields do not all have the same standing, and the table that declares them says which each has (`tab:assayer:harness-scenario-tolerances`): two are figures the specification states, one is the harness's reading of a specification that gives a condition rather than a ceiling, four are the harness's own, and one is exact equality rather than a tolerance at all. One field is a coefficient rather than a bound: the specification states the synchronisation threshold as a coefficient times the dimension (`def:monitoring:synchronisation-error`), so callers take the ceiling from `Tolerances::precision_sync_ceiling` at their own model width and no width is admitted more departure than the specification would admit it.

`testing::drift` holds three budgets for comparisons whose two sides should agree exactly. `PURITY_DRIFT` answers identical-input replays, request-order replays among them. `LIFECYCLE_SUFFICIENCY_DRIFT` and `DIVERGENT_OUTCOME_REPLAY_DRIFT` each sit one decade wider, the first because the compared statistic is reached through a longer chain of sums and the second because resonance is a nonlinear transform of it. All three answer the build rather than the run: the residue they cover is the optimiser's, since the compiler is free to regroup floating-point work it has no reason to keep in order, and the grouping it picks is a property of the whole compilation rather than of the code under comparison. A width measured under one profile alone is a reading of one association among the many a release build may choose, which is why the budgets are set an order of magnitude above the one release residue measured — still four decades below the smallest difference they exist to catch, since what they hold is that two derivations of one assessment agree, and a dependence of that kind moves a tag by a fraction of the tag.

## Liveness · `sec:assayer:testing-architecture-liveness`

Every wait an integration test takes on the label path is unbounded. A flush blocks on an acknowledgement with no timeout, which is the right shape for the engine — a host wants the barrier, not a partial one — but it means a model owner that stops answering leaves the test thread parked in a wait its own loop conditions are never reached from, and the test then reports nothing at all: no assertion fails, no message is printed, and the run ends when whatever is running it gives up.

`testing::liveness` turns that into a failure three ways. `fail_fast_on_model_owner_panic` installs a panic hook that runs the previous hook first, so the owner's own message and location print exactly as they would have, and then ends the process with the failing-test exit status only when the panicking thread's name carries the owner marker — every other thread's panic unwinds normally, so an ordinary failed assertion and a `should_panic` test are untouched. `watch_progress` returns a shared counter and spawns a watcher that prints where the harness has got to every heartbeat, so a run killed from outside still carries its own trail, and ends the process when the counter has not moved for the stall bound; `advanced` and `finished` are the two verbs a driving loop calls. The stall bound is deliberately not a bound on the run: a schedule that legitimately takes a long time is allowed to, and what is never legitimate is one that stops advancing and stays that way. Both are opt-in per test binary and neither is armed by including the module.

`ACK_DEADLINE` and `STATE_DEADLINE` are the third thing and are not opt-in: they are the deadline every bounded acknowledgement wait in the harness and in the crate's own tests is written against. The two are equal, the second defined in terms of the first so they cannot drift apart by accident, and they carry separate names because the call sites read better for it. They are generous rather than tight, and the reason is that they answer a liveness question and never a latency one. The harness sends a command, a loop answers it, and the only thing the wait decides is whether the loop is still answering at all; no test asserts anything about how long the answer took, and a test that wanted to say the answer arrives quickly would have to say so itself with its own assertion on elapsed time. A deadline is not a budget — the wait it bounds is the same wait either way, and it expires only when the answer is never coming — so nothing is bought by failing sooner, while an instrumented coverage build of this crate runs about a hundred times slower and a deadline sized for an ordinary run would fabricate a failure there and leave the suite unmeasurable. A hung loop still fails; it fails later.

## The maintenance harness and the source scanner · `sec:assayer:testing-architecture-side-harnesses`

Two modules serve subjects the `World` does not reach.

`testing::maintenance` drives the crate's internal identity-maintenance thread directly. `MaintenanceHarness` owns the spawned thread and both channels, and its `Drop` sends the shutdown command and joins, so a test never leaks a thread on panic. It declares its own model-owner channel depth, wide rather than derived, so a test draining the receiver after the loop has run never blocks the maintenance thread against it; the figure has no counterpart in a deployment, which is why the harness declares it (`tab:assayer:harness-construction-figures`). Around that sit the vocabulary: two Mudlark configurations, `setup_dimension` for a matching pair of dimension infrastructure and observation channel, registration verbs that wait for the acknowledgement, `checkpoint` for a barrier, `flush_loop` for a barrier plus enough elapsed time that the loop re-enters change detection, three draining verbs over the emitted commands, and a free function that flattens lifecycle events out of a batch of them. One method, `force_decay`, is itself `#[cfg(test)]`, because the command variant it sends is.

`testing::source_scan` factors the shape every repository-hygiene audit shares: walk the source tree, open every Rust file, inspect each line. `SourceTreeScanner` is a builder with directory and file skips and a per-line visitor; `LineVisit` carries the path, the one-based line number, the line and a coarse flag saying whether a test attribute has been seen earlier in the file. The root comes from `manifest_dir`, which reads the manifest directory from the environment at run time rather than baking it at compile time. That distinction is the module's substance: a source audit asks a question about the tree it is being run against, and the compile-time value names whichever checkout produced the binary — a different tree the moment a build cache is shared between clones, in which case the walk would audit somebody else's source while reporting on this one. The compile-time value survives only as the fallback for a binary invoked outside cargo.

## The multi-channel support tree · `sec:assayer:testing-architecture-multi-channel`

The support tree is private to the `multi_channel` binary and compiled once. It is a module tree rather than a set of path includes, which is what makes an item that loses its last caller a finding rather than something a blanket allowance would cover. Its own module documentation says so, and the repository's clippy discipline is the rule behind it (`[INDEX-sec:index:agents-clippy-exception-discipline]`).

Its subject is one seam: what a channel is for cannot bend what the engine believes about the entity behind it. Everything in the tree is scaffolding for probing that seam across many shapes at once, and it layers.

`support::constants` holds three canonical action sets and the three tag sequences they should produce. `support::policy` builds channel policies from an action set, from an action set and a reward block, or from an action set and a perturbation applied to the default rewards; the perturbation form is the shape the whole tree is built around, where two channels share an action set and one changes exactly one decision-layer knob.

`support::rewards` turns that into data. A perturbation case names itself, carries a stable seed salt, an action set, the expected tags and a function pointer that mutates one reward field; nine of them stand in a sweep covering the reward axes one at a time. Two scenario builders declare a baseline channel and a perturbed one, and a single assertion drives one named case end to end.

`support::labels` states observation streams as data. A label-cycle case is entity, action, valence sign, ground-truth flag and an optional challenge outcome, with a method converting it to a `LabelSpec`; a pair holds two such cases for the probes where two worlds should see the same stream but one deliberate difference. Stream constructors produce alternating entity or alternating valence sequences. The driving verbs run one case, a stream of cases, a matched pair across two worlds, or a matched stream — and the matched-stream verb settles both worlds' cold ramps before their histories diverge, because two worlds trained in parallel otherwise reach different accepted counts for no reason but scheduling.

`support::outcomes` trains outcome-axis predictions through ordinary public labels rather than by reaching into model state, in single-world and matched-pair forms, with canonical values and a canonical cycle count. It adds two assertions the library harness has no place for: that every reckoning in a list carries the same prediction, and that two predictions are ordered by raw value with a minimum gap.

`support::assertions` is the tag-level vocabulary. It partitions a profile into action tags and classification tags, counts and sums them, and asserts an exact action-tag sequence. A core-payload expectation bundles the three liveness witnesses — a live reporting Sentinel, a live outcome prediction, an expected signal-degradation footprint — behind constructors that name the combination. The composite assertion states the independence shape in full: the core assessment is fixed, classification tags are fixed, and the action tags must diverge somewhere, with classification asserted separately so the liveness check lands on the action tags rather than being satisfied by an unintended core-side movement.

`support::derivation` is the largest module and holds the matrices. A derivation case is a channel name and its expected action tags; a matrix bundles an ordered case list with the same-action pairs whose action layer must move, so a call site cannot pair one matrix's cases with another's liveness assertions; a request-order matrix adds the reordered case list. Three standard matrices stand as constants — the three-channel independence fixture, the four-channel policy matrix, and the challenge-and-reward matrix — each with its reversed twin. Above them sit the scenario builders and some forty assertion and fixture functions covering same-batch fixed-core comparisons, request-order replays, cross-world batch replays, and the two things a replay may be compared on: the full public core assessment plus the profile, or the sufficient risk statistic plus the profile.

`support::enrichment` crosses all of that with the request shapes the public surface admits. An enrichment is a signal mode of three values, a reported-Sentinel flag, a live-outcome flag and a seed salt; twelve of them form the grid, and the outcome-bearing half is addressable separately. An enrichment knows how to decorate a request for training and for the final assessment, whether the world needs a signal schema, which Sentinel and axis to register, what core payload to expect, which drift budget and which replay comparison its payload warrants, and which health assertion applies — the degraded variants get their own, since a deliberately degraded stream must record sanitised signals while leaving every other degradation counter at zero. Core history is a third axis: a fresh world, a world moved by an alternating label stream, or one moved by an identity dimension plus that stream. The family runners compose the three: for each point in the grid, build a world, prepare the history, train any decision-layer evidence, replay the matrix, assert health.

What it duplicates from the library harness is small and deliberate. The `_with_drift` pairing is the same discipline. `support::labels` re-derives the challenge-routing step that `World::cycle_on` and `cycle_request` already perform, because its paired verb drives two worlds and cannot delegate to either. `support::assertions` and `support::outcomes` wrap library assertions rather than reimplementing them — the classification-tag comparison is the library's tag-profile comparison applied to a filtered slice. What it specialises is everything else: the grid, the matrices, the reward sweep, the channel vocabulary, and the paired-world ceremony, none of which any other binary runs.

## The label vocabulary · `sec:assayer:testing-architecture-labels`

Neither tree mints a claim and neither mints a test. The harness contains no tests of its own, so nothing in either carries a `test:` label; the tests that use the harness mint their own, and a reader tracing a helper to its callers does so through the generated per-file indexes rather than through a citation.

Each tree does mint exactly one table, and in both cases it is the generated folder matrix, and in both cases it is empty — one saying the folder holds no unit tests, the other that it holds no integration tests. That is the correct reading of a tree that is scaffolding and not subject matter, and it is the only structural evidence in the corpus that says so.

What the harness mints beyond that is figures. Sixteen constant heads stand across four modules, each with an algorithm citation and a form or count pin beside it: twelve in the report fixtures — the routing coordinate, its three derived cell prefixes, and the four peak and four accumulator ladders — plus the command-channel capacity, the model-owner channel depth, the clock epoch, and the tolerance bundle as a single form. Every one is registered in a table that gives its reason, because the obligation to declare a figure is not the reason the figure has the value it has, and the tables exist so that no harness value has to cite a head that does not fix it (`sec:assayer:harness-declarations`).

What the harness cites is the corpus it is scaffolding for. The clock module cites the two-domain decision three times; the world module cites the reader's obligations, the channel preemption order, the per-request load, the score-before-evolve ordering and the evidence-authority invariant; the assertion module cites the report-only invariant, the in-band travel corollary and the never-failing cascade; the drift module cites three measurement entries. The support tree cites claims almost exclusively: thirteen distinct claim heads across sixty-nine of its eighty-two citations, of which the channel-independence claim alone accounts for twenty-seven — a fixture cites the promise it exists to let a test witness.

## Observations · `sec:assayer:testing-architecture-observations`

**Observation (The harness reaches three surfaces, not two)** · `obs:assayer:testing-architecture-three-surfaces`

The feature comment and the module documentation both describe the harness as shared between crate tests and integration tests. There is a third consumer: thirteen production source files carry inline test modules that name `crate::testing` directly, and those tests mint under `test:unit:` rather than under either of the other two areas. One of them reads the tolerance bundle for a bound the module under test is itself about. Nothing is wrong with the arrangement — the gate that admits the crate's own test build admits an inline module as readily as a module in the test tree — but a reader taking the two-surface description literally will underestimate the harness's blast radius by thirteen files.

**Observation (A harness helper that loses its last caller is not reported)** · `obs:assayer:testing-architecture-unreported-decay`

The module documentation states that gating what compiles rather than only what is visible means a helper that genuinely loses its last caller is reported. That holds for the sealed build, where nothing but the clock compiles, and it does not hold for the build the suite runs in. There the module is `pub`, so every item flattened out of it is part of the crate's public API and no unused-code lint can fire on one. Seven items presently have no caller outside the module that defines them: `VirtualClock::travel_to` and `VirtualClock::travel_to_nanos`, `World::label_with_challenge_result`, `WorldBuilder::tolerances`, `ModelOwnerBlockGuard::release`, `SourceTreeScanner::skip_file`, and `MaintenanceHarness::drain_lifecycle_events`. An eighth, `init_tracing`, is re-exported but called only by the two scenario constructors beside it. Each is reachable and each is documented; none is reported.

**Observation (The deadlines are liveness numbers and not latency budgets)** · `obs:assayer:testing-architecture-deadlines-are-liveness`

`ACK_DEADLINE` and `STATE_DEADLINE` are five minutes, which reads as an extraordinary latency allowance and is not one. Nothing in the suite asserts that an acknowledgement arrives within them; they exist so that a loop that has stopped answering makes its own test fail with a message naming the wait, instead of parking the test thread until the runner gives up on the whole run. Sizing them down would buy nothing, because the wait they bound is the same wait either way, and would cost the coverage job, whose instrumented build runs about a hundred times slower than an ordinary one. A test that wants to say something about how quickly an answer arrives has to assert on elapsed time itself.

**Observation (One integration target carries its own copy of the liveness module)** · `obs:assayer:testing-architecture-liveness-copy`

The synchronisation-drift target defines local equivalents of all four liveness items — the failure status, the owner-thread marker, the progress type, the panic hook, the watcher, and the two counter verbs — rather than importing them, and its own module header says the copies are deliberate and names the condition under which they should be replaced by imports. The condition it names has since been met: the harness now lives in the library and the items are re-exported. Two other targets import the library's versions. The copies and the originals have drifted a little in their messages and in the order of the watcher's branches, though not in behaviour.

**Observation (Some staging notes name items the trees do not contain)** · `obs:assayer:testing-architecture-staging-notes`

The module documentation of the harness and of the world describes a staged plan, and several items named in it do not exist. The verb table names a world-level advance verb and a label-tape injection verb; the staging list names a label tape, a report tape and a converged-world factory; the report module's own header lists a pre-computed golden-values type. None is defined anywhere in the package. Time travel is reached instead through `World::clock`, which hands back the shared clock a test then advances. Two entries in the same table have gone the other way and are marked as pending work that has since landed: the assessment verb and the batch assessment path are both present. The documentation is therefore neither a reliable roster of what exists nor a reliable list of what does not.

**Observation (The two trees mint one empty table each and nothing else structural)** · `obs:assayer:testing-architecture-empty-matrices`

Both folders carry a generated matrix that reports no tests. That is the only structural marker distinguishing a scaffolding folder from a test folder in the corpus: there is no separate declaration that a folder is scaffolding, and the matrix's emptiness is what a reader has to infer it from. It is also load-bearing in one direction — the matrix is computed and compared against the committed bytes on every run, so a test placed in either folder by accident would be caught by the mismatch.

**Observation (One maintenance verb is reachable from crate tests only)** · `obs:assayer:testing-architecture-crate-only-verb`

`MaintenanceHarness::force_decay` carries a `#[cfg(test)]` of its own, because the maintenance command it sends is itself test-only. The attribute is satisfied by the crate's own test build and not by the `test-support` feature, so the four call sites are all in the crate test tree and an integration target cannot reach the method however the feature is set. It is the only item in either tree whose availability differs between the two gates.

**Observation (The paired-world verb re-derives the challenge-routing step)** · `obs:assayer:testing-architecture-routing-duplication`

The decision to route a challenge outcome to the companion tracker before submitting the core label — read the specification's action, read its optional outcome, record it if both are present — is written four times: once in `World::cycle_on`, once in `cycle_request`, and twice in `cycle_request_pair`, which drives two worlds and so cannot delegate to either single-world verb. The four copies agree. The duplication follows from the shape of the paired verb rather than from oversight, and it is the only substantive logic the support tree restates from the library harness.
