# The shared testing contract becomes an executable harness · `plan:assayer:harness-implementation`

This plan is the engineering route from the observed testing architecture (´rep:assayer:testing-architecture´) to the shared testing contract (´rec:harness:shared-testing-contract´). It fixes no new product or harness decision: the record owns the end state, the concept supplies the sized shapes, and the campaign backlog remains the only register of entry state (´sec:assayer:testing-harness-concept-changes´) (´sec:assayer:campaign-testing-harness´).

## The finished harness · `sec:assayer:harness-implementation-finished`

The finished library harness is the set declared by `testing::mod` and transcribed below. The private multi-channel support tree remains a specialised harness; it delegates common scenario, routing, barrier, playback, and fixture behaviour without surrendering its grid, matrices, reward sweep, channel vocabulary, or paired-world ceremony (´dec:harness:specialised-side-harnesses´).

Both tables describe the modules as they stand. Where an open entry will extend one, the extension is named in that entry's route rather than written into a roster row, because a roster that promised surfaces would stop being the transcription of what `testing::mod` declares, and the backlog would stop being the only register of entry state. One consequence is visible in the support roster: the alternating label history is the stimulus the runner's contract qualified and it is the one that moved, while the tree's other repeated stimuli still drive their rows directly, which the contract permits because it admits a long stimulus to the runner rather than requiring every repetition to enter it (´entry:assayer:harness-tape-runner´) (´dec:harness:declarative-playback´).

The resulting caller inventory has fifty-eight crate test modules, twenty-four integration targets, seven inline production test modules, and one benchmark target. The crate figure counts the modules the crate test tree declares, and it moved rather than holding stable: focused coverage for the oracle tier, the tape runner, the persistence fork, the seeded packs, and the production clock sites landed as its own modules instead of extending the subject modules that already owned those APIs, while the retired stopwatch module left with its target. The integration figure counts the targets the package's integration directory declares, where the three topic targets added beside `learning_convergence` account for the increase (´dec:harness:convergence-split´). The inline figure counts a production source file once when a `use` or a path expression inside its inline test module names a gated `testing` item, and never counts the ungated `Clock` and `SystemClock` pair wherever it appears, because production reads its time through that pair in every build and naming it is not reaching the gated surface. Two further production files name only that pair inside their inline tests and four more reach it from production code alone, so neither group is a caller of the harness. The single Criterion target accounts for the benchmark surface (´sec:assayer:performance-harness-measurement-contract´).

The end state contains no parallel crate configuration, entity, report, or wait vocabulary; no public raw scenario-clock handle; no test-authored sleep, poll, deadline, or compound wait outside `testing::liveness`; no private copy of the common liveness helpers; no duplicated challenge-result routing step; no callerless exported helper; and no staging note that names an absent item or calls a present item future work. The specialised maintenance seam and the multi-channel grid, matrices, rewards, row shapes, and paired-world ceremony remain because their subjects are genuinely local (´dec:harness:specialised-side-harnesses´).

The shapes fixed by the record and concept are carried rather than reconsidered: one barrier verb is named for each queue and states coverage and exclusions; `World::advance` and `World::travel_to` move only forward by delegating to `VirtualClock` and then crossing the required barriers; playback accepts subject-owned rows through a trait; probes cross a barrier and load once before returning owned values; and a fixture returns only after its own named precondition holds (´sec:assayer:testing-harness-concept-time-and-barriers´) (´sec:assayer:testing-harness-concept-tapes´) (´sec:assayer:testing-harness-concept-probes´) (´sec:assayer:testing-harness-concept-guarded-fixtures´).

## Contributor conventions · `sec:assayer:harness-implementation-conventions`

1. A reusable Assayer-owning test capability belongs under `testing`; a subject-specific row, matrix, or paired ceremony stays with its subject, because a second owner of common queue semantics creates a second contract. A violation is a crate, integration, inline, or support module that constructs common scenario state or declares common barrier meaning locally (´dec:harness:single-scenario´) (´dec:harness:specialised-side-harnesses´).
2. Every harness module except `testing::clock` carries the `cfg(any(test, feature = "test-support"))` compile gate of the harness surface, or a stricter gate that excludes it from more builds still — the durable modules add the serialisation feature, and the comparison pair narrows to the crate's own test build — because visibility alone would leave unreachable crate-private test code compiled in a sealed library. A violation is any non-clock harness item present in a featureless library build (´sec:assayer:testing-architecture-reach´).
3. A submodule is `pub` only when callers must name its path; otherwise the module stays private and its intended items are flattened through `pub use`, because the shortest stable caller vocabulary exposes items without exposing implementation compartments. A violation is a public module with no path-naming caller or a caller forced through a private implementation path (´sec:assayer:testing-architecture-reach´).
4. `World` owns the real `Assayer`, its clock, name registry, policies, tolerances, and declarations; probes and fixtures return owned projections, never borrows or mutation handles into that state, because one scenario coordinates but never becomes another product-state owner. A violation is an exported `NameRegistry`, a handed-out mutable engine component, a retained published borrow, or a probe with a mutation path (´dec:harness:single-scenario´) (´dec:harness:probe-contract´).
5. Tests move time only through forward-only `World` verbs and wait only through the barrier named for the queue whose completion they need, because a raw clock cannot know which asynchronous work its movement activated and elapsed time proves no queue drained. A violation is direct test use of `VirtualClock`, a sleep, poll, local deadline, compound wait, or inference from one barrier about an excluded queue (´cor:clock:harness-control´) (´cor:concurrency:harness-barriers´) (´dec:harness:no-ad-hoc-waits´).
6. A probe crosses its relevant barrier, performs exactly one published load, returns an owned read-only projection, uses scenario time, and preserves retention exclusions, because mixed versions, retained borrows, and widened host state all invalidate the reading. A violation is a multi-load projection, an engine borrow, mutable access, an external clock, an excluded precision field, or a probe reachable from a sealed host build (´dec:harness:probe-contract´) (´cav:retention:probe-boundary´) (´cor:surface:test-support-opacity´).
7. A long stimulus supplies subject-owned typed rows to the shared runner, and the runner alone owns barrier cadence, checkpoint callbacks, bounded batches, and progress, because those are execution semantics rather than properties of the subject row. A violation is a hand-written long loop that chooses its own settling cadence or treats one batch as one published view (´dec:harness:declarative-playback´) (´cor:ordering:tape-batches´).
8. A shared oracle has several callers, states whether its route is a specification formula, independent derivation, or harness reference, and has a deliberately defective arm, because route reuse can otherwise test only self-consistency. A violation is a one-caller oracle, omitted provenance, production-route reuse, or no fails-before witness (´dec:harness:oracle-tier´) (´cav:harness:oracle-trust´).
9. A state-establishing fixture checks its named precondition and reports the measured baseline before returning, while the result oracle remains separate, because setup failure and result disagreement demand different remedies. A violation is unchecked setup, a hoped-for threshold with no measured baseline, or one assertion that conflates guard and result (´dec:harness:guarded-fixtures´) (´dec:harness:separate-validation´).
10. The package's self dev-dependency alone enables `test-support` for every unit, crate, integration, and benchmark build and never for a host build, because callers should not select the gate independently. A violation is a test target that adds its own feature ceremony or a normal dependency that makes the harness host-reachable (´sec:assayer:testing-architecture-reach´).
11. A new harness module updates the roster documentation, the declaration and re-export set, its existing subject-module test index, and the generated folder matrix to a fixpoint, because the roster and projections are the checked inventory of what exists. A violation is a module absent from the roster, an orphaned exported item, a stale test index, or a nonempty scaffolding folder still projected as empty (´sec:assayer:testing-architecture-roster´) (´obs:assayer:testing-architecture-empty-matrices´).
12. Harness scaffolding mints neither a claim nor a test label; each test that consumes it mints its own label at its standard place, and every authored fixture figure carries its registered reason, because the harness supplies mechanism while the caller owns the behavioural assertion. A violation is a claim or test mint in scaffolding, a bare cross-test inventory citation, an unindexed test, or an unexplained fixture literal (´sec:assayer:testing-architecture-labels´) (´conv:assayer:golden-pin-churn´).

## The incremental route · `sec:assayer:harness-implementation-route`

The route lands replacement capability before migration and migration before deletion. Every intermediate commit keeps old and new callers compiling, adds focused coverage for the new surface before moving a caller, moves callers in subject-sized batches whose corpus projections can be checked independently, and deletes the old vocabulary only after a recognizer proves that no caller remains (´sec:assayer:testing-harness-concept-migration´).

The three retirement routes below have run to completion and are kept as the record of what executed, each with the recognizer that closed it; a route that named its recognizer is the evidence that the deletion was safe, and deleting the route would leave the deletion unexplained. The capability routes after them are the ones still to run, and they add surfaces rather than retiring vocabulary, so each names the module it lands in, the decision that bounds it, and what proves its entry closed.

**Step (Scenario-unification retirement route)** · `step:assayer:harness-scenario-unification`

The complete builder and closed barriers landed before their parallel configuration and wait vocabularies moved, the standing shared report fixtures replaced crate report constructors, and the first support bite centralised challenge-result routing; crate modules then replaced configuration, entity, report, and wait helpers in gate-able subject batches, maintenance adopted the common barrier while retaining its seam, and multi-channel support delegated only common behaviour while retaining its specialised rows and paired ceremony. Because dead code is denied, each parallel declaration left in the subject batch that removed its last caller, including `ScenarioBuilderExt`; the final retirement boundary then ran the recognizer across every crate, integration, inline, and benchmark caller, required fixture setup to enter through `testing::Scenario` or `testing::World`, found none of the retired helper declarations, and left the generated roster, per-file indexes, and folder matrices clean (´entry:assayer:harness-scenario-unification´) (´cav:harness:incremental-adoption´).

**Step (Polling-and-waits retirement route)** · `step:assayer:harness-polling-retirement`

The closed queue-barrier set landed with focused coverage first; callers of the stale version poll and each sleep site then migrated in queue-specific batches, with every changed test naming the replacement barrier and preserving a liveness failure through `testing::liveness`; the last commit deleted the version-wait helper and sleeping maintenance flush. The recognizer searched all test and harness sources for authored sleeps, polling loops, deadlines, and wait helpers outside `testing::liveness`, rejected any unclassified occurrence, and required each removed site to be paired with its named barrier. It ran once: the retained sites carry their own rulings, and nothing repeats that search on the next commit, which is the gap the guardrail entry exists to close (´entry:assayer:harness-polling-retirement´) (´dec:harness:no-ad-hoc-waits´) (´entry:assayer:harness-convention-checker´).

**Step (Callerless-helper and staging-note retirement route)** · `step:assayer:harness-stale-helper-retirement`

The moved-base census searched inline, crate, integration, benchmark, and harness callers after scenario time, probes, fixtures, and the settled barriers had landed. Live clock-travel and model-owner release paths remained; every residual callerless entry point and its private supporting state retired, the tracing initializer stopped being flattened, and the module prose was rewritten against the declarations. Commit `edd8582d9` had already replaced the synchronisation-drift target's liveness copies with imports. The recognizer combines the generated orphan check with source searches for the retired names and requires module prose, declarations, re-exports, and the roster to agree (´entry:assayer:harness-stale-helper-retirement´) (´obs:assayer:testing-architecture-unreported-decay´) (´obs:assayer:testing-architecture-liveness-copy´) (´obs:assayer:testing-architecture-staging-notes´).

The supplied spine through barriers, polling retirement, scenario time, probes, runtime evidence, and playback gave the sweep enough information to distinguish adopted capability from residue. The persistence fork was a consumer of those supplied capabilities rather than a prerequisite of the completed retirement, and the guarded fixtures, oracles, convergence layout, performance, production-clock, and seeded-pack work branched where the dependency table then permitted. All of it has landed, so what the route carries forward is not a construction order but the demand the finished harness is still asked for, grouped by the module each addition lands in (´sec:assayer:campaign-testing-harness´).

**Step (Owned-reading additions route)** · `step:assayer:harness-demanded-readings`

Twelve owned projections land in `testing::probes` behind their `World` entry points, and the thirteenth, the channel posterior, lands on `World` itself because it resolves a host-owned provider rather than projecting published engine state. Each arrives with its focused test before the next, and each is bounded by the probe contract rather than by a widened host surface: one barrier crossing, one published load, an owned copy, scenario time, no borrow or mutation route, and no precision field (´dec:harness:probe-contract´) (´cav:retention:probe-boundary´). Nine close on that evidence alone; the other four close only when the production value they read is published, which is work their own plans hold. The recognizer is the thirteen named projections reachable through the scenario, each with its barrier-freshness, one-version and no-mutation witness, a featureless build that still leaves the probe module and its re-exports uncompiled, and, for the four, closing evidence that names the production entry which supplied the value rather than assuming it (´entry:assayer:harness-demanded-readings´).

**Step (Guarded fixture and population additions route)** · `step:assayer:harness-demanded-fixtures`

Four fixtures land in `testing::fixtures` and two in `testing::performance`, each beside the population it declares: the matched alarming-and-normalised report pair over the fixed geometry in `testing::reports`, the dense-conditioning growth fixture driving bounded typed rows through playback, the trained Sentinel pair factored out of the slot-legibility target so a second training path does not survive beside it, the sparse-reporting interaction fixture on the landed template seam, and the equal-width ill-conditioning pair with the paired cadence-and-cost sampler that reads it through the landed label-update recorder. None is a widening of the shared trained state, whose score-verified schema and default construction are fixed, so each is a second fixture rather than a loosened first (´entry:assayer:harness-guarded-fixtures´). The recognizer is that every added fixture returns only after checking its named precondition and reporting the measured baseline beside its declaration, that each carries a refusal witness invalidating one declared fact and checking the complete diagnostic, and that no guard doubles as the result oracle (´entry:assayer:harness-demanded-fixtures´) (´dec:harness:guarded-fixtures´) (´dec:harness:separate-validation´).

**Step (Persistence-fork extension route)** · `step:assayer:harness-fork-extensions`

The crash-tail image builder, the invocable durable comparison, and the replayable registration tape extend `testing::fork` and the crate-internal projection behind it, each with focused coverage before the next; every arm continues to restore under the one injected clock and to apply elapsed decay once, which is the boundary the durability corollary drew (´cor:durability:harness-fork´). The comparison is the one addition that crosses a gate rather than a module: an integration target can reach it only through an opaque operation on the fork, because the field-addressable projection is gated to the crate's own test build and flattening it would put precision into an integration-reachable surface (´dec:harness:probe-contract´). The recognizer is an unabsorbed journal tail surviving capture, independently owned roots whose journals do not alias, a rebuilt arm carrying its caller's configuration, a named first difference for a deliberately perturbed field, and a restored arm whose identifiers and runtime layout are unchanged after replay (´entry:assayer:harness-fork-extensions´).

**Step (Multi-world playback entry point route)** · `step:assayer:harness-paired-playback`

The paired entry point stands beside the landed single-world runner and shares its row trait instead of replacing it, because the row contract reserves settling cadence for the runner and a row that flushed its partner itself would take that cadence back (´dec:harness:declarative-playback´). It crosses the selected policy on each world a row touches, in declaration order, before that row's checkpoint and progress boundary. The recognizer is a focused witness that fails if either world's barrier can be skipped or run late and that names the blocked row without depending on the barrier set's internal shape, with row order, per-request publication semantics, checkpoint observations, and progress boundaries unchanged by batch size, and progress still liveness evidence rather than a latency reading (´entry:assayer:harness-paired-playback´) (´cor:ordering:tape-batches´) (´cav:harness:progress-not-latency´).

**Step (Support-tree addition route)** · `step:assayer:harness-support-tree-additions`

The exchangeable challenge-provider fixture lands in the tree's derivation support and the exhaustive replay comparator in its assertion support, both inside the specialised boundary: they are subject-specific ceremony for the multi-channel grid, and moving either into the shared harness would give common behaviour a second owner while giving these two callers nothing (´dec:harness:specialised-side-harnesses´). The recognizer is a replacement driven through the public trait and its default posterior, and a field-complete comparator that fails on any single changed field where the existing purity witness compares a partial fingerprint, with no shared engine logic or queue barrier moved into the tree and no host-owned control added to the scenario (´entry:assayer:harness-support-tree-additions´).

**Step (Convention-checker adoption route)** · `step:assayer:harness-convention-checker`

The rule set, its admissible exceptions, and the adoption are this package's work; the mechanism is not built here, because a recognizer only this package could run would leave uncovered exactly the surfaces a violation arrives on — crate tests, integration targets, inline tests, benchmarks, and the retained support tree alike — while the repository's linter already reaches all of them as a checked policy, which is the arrangement the register-projection adoption established (´entry:assayer:harness-convention-checker´) (´entry:assayer:tool-generated-registers´). The conventions above supply the argued obligations and their recognizable violations, so what the entry chooses is which of corpus naming, a source audit, or compile fixtures enforces each. The recognizer is a repeatable check that rejects, each with its site, a test-authored sleep, poll, or wait outside `testing::liveness`, a second declaration of common scenario state, and a second barrier meaning; that keeps the six ruled and retained stimulus sites admissible beside their rulings instead of reopening them; that carries a deliberately violating arm per rule; and that runs clean over this package with no crate-wide exception (´tab:assayer:harness-polling-retirement-census´).

Each capability route is bounded by the module its entry names and by the decision that entry cites, and each lands its focused coverage before the surface it covers is consumed elsewhere, which is the order the retirement routes used for replacement capability. Two obligations get no route here. The compile-fail runner would be one target and one fixture per witness, but it waits on a recorded decision about a compile-fail development dependency, and writing its route first would decide that question by analogy (´entry:assayer:harness-compile-fail-runner´). The registration-lift ruling has no harness surface at all: every mechanism its eventual witness needs is present, so what it waits on is the corpus choosing what the promise means, not this plan (´entry:assayer:harness-registration-lift-ruling´).

## Dependency analysis · `sec:assayer:harness-implementation-dependencies`

A hard dependency means the dependent entry cannot meet its acceptance before the prerequisite lands. A soft dependency means implementation can start and close first, but the dependent surface would be rewritten when the prerequisite arrives. ## Rejected alternatives · `sec:assayer:harness-implementation-rejections`

Doing the retirements first was rejected, and the routes above ran in the other order for that reason. The decisions those retirements enforce had no complete replacement in the tree when they were proposed: removing waits before the closed barriers would have removed working tests, deleting clock travel before scenario time would have caused delete-and-restore churn, and deleting parallel scenario helpers before their callers could express the same setup through `WorldBuilder` would have made the tree red (´sec:assayer:testing-harness-concept-migration´).

One grand harness lane is rejected. Its changes concentrate in `testing::world`, the crate helper tree, support modules, test indexes, and the backlog; no intermediate gate can certify which replacement is sound, and one failure discards the separable progress the dependency graph exposes (´obs:assayer:testing-harness-concept-destination-concentration´).

Leaving conventions as descriptive observations is rejected. Every implementing lane would have to infer placement, gating, visibility, ownership, labels, fixtures, and wait discipline again, and different inferences would recreate the parallel contracts the single-scenario decision removes (´dec:harness:single-scenario´).

Landing a checked convention rule in this plan is rejected. A recognizer must enforce an argued obligation whose violation is already stated; this document supplies that argument, while the guardrail entry that now owns the rule set chooses the checker and its corpus reach without making an unexplained rule authoritative (´entry:assayer:harness-convention-checker´).

## Risks and open questions · `sec:assayer:harness-implementation-risks`

**Observation (Playback and persistence now have one route)** · `obs:assayer:harness-implementation-playback-persistence`

The earlier route conflict is resolved: the measured runtime evidence enabled playback, and the closed barrier set that was its unsupplied prerequisite has since landed with its coverage and exclusions witnessed (´entry:assayer:process-grid-runtime´) (´entry:assayer:harness-closed-barriers´). The durability corollary placed the persistence witness after playback, the route ran in that order, and the fork closed as a consumer of the supplied surfaces; both entries therefore leave the row set, and the corollary is now a citation at the consumption site rather than a graph link (´cor:durability:harness-fork´) (´entry:assayer:harness-persistence-fork´) (´sec:assayer:campaign-strategy´).

**Observation (Clock-domain control is typed rather than independently skewable)** · `obs:assayer:harness-implementation-clock-domain-shape`

The separation required by the clock corollary is carried by distinct persistent and intra-process types with no conversion between them, while one `VirtualClock` offset preserves their relationship and the concept fixes one `advance` and one `travel_to` pair (´cor:clock:harness-control´) (´sec:assayer:testing-architecture-clocks´) (´entry:assayer:testing-harness-concept-time-verbs´). `World::advance` and `World::travel_to` therefore move both typed readings together: independent domain verbs would permit a skew no engine behaviour needs, would contradict the one-handle clock shape, and would add a second verb pair without strengthening the type boundary. The scenario-time API is closed on distinct typed readings, not independently movable presents (´entry:assayer:harness-scenario-time´).

**Observation (Performance playback never needed a settled entry edge)** · `obs:assayer:harness-implementation-performance-playback-edge`

The performance plan says long setup streams use declarative playback (´sec:assayer:performance-harness-shared-scenario´), while the Criterion target's contract named only the supplied projections and fixtures as prerequisites (´entry:assayer:performance-criterion-target´) (´entry:assayer:performance-benchmark-projections´) (´entry:assayer:performance-harness-fixtures´). No row-to-row edge was added and none was needed: the scheduled route consumed the supplied target rather than its setup implementation, and every one of those entries closed without waiting on the tape runner. The same reading governs what is left. The two additions still asked of `testing::performance` — the equal-width ill-conditioning pair and the paired sampler that reads it — consume the landed runner and the landed label-update recorder at their setup sites, so they stay inside their own entry instead of acquiring an edge to a capability that is already supplied (´entry:assayer:harness-demanded-fixtures´) (´entry:assayer:harness-tape-runner´).

**Observation (Convention enforcement has an owner for the rule set and a home for the mechanism)** · `obs:assayer:harness-implementation-convention-enforcement`

The conventions state recognizable violations, and the guardrail entry owns the rule set, its admissible exceptions, and the adoption, while the mechanism belongs to the repository's linter as a checked policy rather than to this package (´entry:assayer:harness-convention-checker´). The reason no rule lands in this plan is unchanged: a recognizer must enforce an argued obligation whose violation is already stated, a rule written here would be authoritative without having been argued, and the choice between corpus naming, a source audit, and compile fixtures is precisely what the entry has to make. What this plan supplies is the argument the eventual checker enforces, and it weakens no obligation into a suggestion while the checker is pending.

**Observation (The parked runner's prerequisite is a decision, not an entry)** · `obs:assayer:harness-implementation-compile-fail-boundary`

The compile-fail runner's row names a recorded decision as its prerequisite, and no entry mints that decision: the campaign's ruling queue holds the registration lift alone, and a parked entry's revisit condition is not an active ruling (´entry:assayer:harness-compile-fail-runner´) (´sec:assayer:campaign-strategy´). Naming the boundary the decision must be taken against is therefore the most the graph can carry, because the seeded-sweep decision refused a property-testing framework on grounds that do not reach a build-time diagnostic dependency, so neither admitting nor refusing follows from it (´dec:harness:seeded-sweeps´). Inventing a ruling row here would create the owning entry the backlog deliberately does not have, while leaving the row out would hide the one edge that makes the entry unschedulable.

**Observation (The playback revisit condition is satisfied)** · `obs:assayer:harness-implementation-playback-revisit`

The enrichment-grid runtime entry records its maintained command, baseline distribution, tolerance, and overloaded-rerun rule, so the exact revisit condition has fired (´entry:assayer:process-grid-runtime´). Playback then landed as an engineering entry, its remaining hard prerequisite — the closed barrier set — having been supplied first, so the route the condition governed has run (´entry:assayer:harness-tape-runner´) (´entry:assayer:harness-closed-barriers´).

**Observation (Shared files are a scheduling risk, not dependencies)** · `obs:assayer:harness-implementation-shared-file-risk`

Most lanes touch the backlog, module declaration, `World`, or generated indexes. Those collisions require hunk ownership and ordered integration, but they do not create dependency edges unless one entry consumes another's capability; treating merge convenience as an edge would erase useful parallelism without improving correctness.

**Observation (Harness completion does not settle product blockers)** · `obs:assayer:harness-implementation-limited-unblocking`

The finished harness removes duplicate construction, observation, and completion machinery but supplies no missing production behaviour and settles no specification alternative. An absent subject or unsettled contract remains an external prerequisite after the harness becomes descriptive (´cav:harness:limited-unblocking´).
