# Construction · `rec:construction:validated-lifecycle`

This record owns how an instance comes into existence and how it is reshaped afterwards: what the builder validates, which of the two starts it takes, and what a lifecycle change makes visible and when. It realises the construction choice (`dec:contracts:construction-surface`) and the lifecycle choice (`dec:contracts:lifecycle-surface`).

It is the one record in the set that names parameters. Every numeric default the runtime surfaces reason about is a parameter of this contract, which is why they can decline to state any (`cav:surface:no-local-figures`) — and why the table here names the parameter and its site rather than transcribing its value.

**Decision (The builder validates eagerly)** · `dec:construction:eager-validation`

The builder validates the signal schema, the interaction templates and every numerical parameter before it returns an instance, so a misconfiguration fails at construction rather than at first use (`req:host:construction`). The schema is required and may be empty; leaving it out is an error rather than a default (`src/api/builder.rs`).

Eagerness is worth deciding because the alternative fails late and quietly. A parameter validated at first use is validated on a path that has already promised it cannot fail, so the only remaining options there are degradation or a panic — neither of which tells the host what it actually got wrong. Requiring the schema explicitly follows the same reasoning: a host that forgets it should learn at build, not from a deployment that silently learns nothing.

**Decision (Configuration is Core-only)** · `dec:construction:core-only-config`

The builder accepts Core configuration and nothing else. Derivation configuration and Companion configuration are host-owned, supplied at call time to the functions that need them, and the builder has no place to put them (`src/config/types.rs`).

The exclusion is structural rather than advisory. The Core has no concept of channels or of what an action is worth, so a Core that accepted channel policy would be storing a value it could only pass back out — and a stored copy is a second source of truth that drifts from the one the host passes per call. Keeping the boundary at construction is what makes the assessment surface's refusal of channel input coherent rather than arbitrary (`dec:surface:no-channel-input`).

**Decision (Construction either cold-starts or restores)** · `dec:construction:two-starts`

There are two starts and no third. The builder attempts a restore where one is configured and cold-starts otherwise; a checkpoint that is structurally incompatible cold-starts as well, with a warning rather than an error (`src/api/builder.rs`).

Falling back rather than failing follows from what the host asked for. The intent expressed by building an instance is *start*, and a restore is an optimisation on that intent, not a precondition of it — so a corrupt or mismatched checkpoint should cost the learned state, which is recoverable, rather than the instance, which is not. What counts as compatible is the durability record's (`dec:durability:structural-compatibility`): structure must match, numerical parameters may change across the boundary.

That reasoning covers a checkpoint the restore cannot use and stops there, so one case falls outside it and takes the other disposition. Where the file is absent, unreadable, or laid out against a structure this build does not have, there is nothing to resume and the fallback costs the host nothing it had; the learned state was already out of reach before the builder looked. Where the file was read, its structure agreed, and what it carries is a precision matrix the model's invariant does not admit, the state is not out of reach — it is there, and one matrix in it is wrong. Cold-starting then is not an optimisation declined but a decision taken on the host's behalf, and taken the way the host would least likely have taken it: an earlier checkpoint may be intact and the journal may be replayable, and the builder knows about neither. So that one case fails the build and the refusal names the model and the pivot (`dec:posterior:cascade-never-fails`), (`dec:degradation:error-partition`). This does not add a third start. It says that the restore start can end in a refusal the host is told about, rather than silently becoming the cold one.

**Decision (Threads are spawned at build and named per instance)** · `dec:construction:named-threads`

The background threads are spawned during the build, and each carries a name derived from the instance's own identifier (`src/lib.rs`). The maintenance thread is spawned whether or not anything has yet been registered for it to maintain.

Naming per instance is what makes a stall attributable in a process running more than one instance, which is the case the anonymous alternative silently fails. Spawning unconditionally is the smaller decision and the same kind: a thread that appears only once some entity is registered is a thread whose absence and whose failure look identical from outside. An idle thread waiting on its channel costs nothing and is observably present.

**Decision (Pre-seeding is a post-construction step)** · `dec:construction:post-seeding`

Pre-seeding is a separate synchronous call made after construction and after every entity it refers to has been registered, not an argument to the builder (`alg:host:pre-seeding`). It blocks until the steward has processed every entry (`src/api/preseed.rs`).

Post-construction is forced by ordering: seed entries name Sentinels and axes, which are registered at runtime through the lifecycle methods, so a builder argument would have to carry entries referring to entities the builder cannot have created yet. Blocking is the deliberate half — it lets a host verify what the seeding achieved before serving traffic, which an asynchronous seed would turn into a race between warm-up and first request.

**Decision (Lifecycle is six operations)** · `dec:construction:six-methods`

Registration and deregistration for Sentinels, outcome axes and identity dimensions: six operations, each taking a shared receiver and each returning a result (`src/api/lifecycle.rs`), over the operations the specification tabulates (`tab:registry:sentinel-operations`) and (`tab:registry:axis-operations`).

The shared receiver is the decision worth naming. These calls run concurrently with assessment and labelling, so requiring exclusive access would make every lifecycle change a stop-the-world event and would push hosts toward batching them for the wrong reason. Identifiers are supplied by the host rather than minted here, which is why the result carries no identifier back: the package enforces uniqueness over a namespace it does not own.

Two of the six removals carry a disposition, so the surface is eight calls over the six operations: a Sentinel and an outcome axis may each be removed destructively or hibernating (`alg:registry:hibernation`), (`entry:construction:hibernation`). The disposition is a separate call rather than an argument because it is a separate decision with a separate consequence — one leaves an archived block behind and one does not — and a surface that made it a flag would let a host take the archiving path by defaulting into it. Everything else the removal does is identical under both, which is why the count of *operations* did not move.

**Decision (Visibility is two-phase)** · `dec:construction:two-phase-visibility`

Infrastructure becomes visible synchronously, before the call returns; the model follows asynchronously, at the next publication (`inv:guarantee:lifecycle-publication`). Between the two the system runs with the infrastructure present and the model not yet extended.

That interval is a designed operating mode and not a defect. It exists because writes are serialised through one steward (`dec:concurrency:single-steward`), so the model cannot change on the caller's thread, while the infrastructure must exist immediately or reports for a new Sentinel would have nowhere to land. The transitional state is self-correcting: features resolve to zeros until the extension publishes, which is the same shape as a registered Sentinel that has not yet reported.

**Decision (Identity deregistration blocks)** · `dec:construction:blocking-deregistration`

Removing an identity dimension blocks the caller until the published snapshot has stopped referencing it, and only then is its infrastructure destroyed (`src/api/lifecycle.rs`). It is the one lifecycle call that waits on the steward.

The block closes a window rather than buying tidiness. Without it the entry can be removed while a reader still holds a snapshot naming the dimension's feature indices, which leaves assembly resolving indices against a contract that no longer describes anything — a state no reader can detect. Ordering the publication before the removal eliminates it. The cost is a slow call on a rare event, which is the right trade for a deployment-scale operation.

**Decision (A compound batch continues past non-fatal failures and publishes once per order-free chain)** · `dec:construction:compound-batch`

Several lifecycle events submitted together are walked in order by the steward and gathered into maximal chains of operations that are *order-free* with respect to one another — operations that, applied in either order, publish the same state. Each chain is applied as one plan computed entirely against the layout the previous publication left, with one rebuild of the dimension map and one publication per chain (`req:registry:compound-events`). A handler that cannot complete its event does not terminate the batch, and completion is signalled once, after the last chain.

Publishing per chain rather than per event is the visible half, and the reason is the one that ruled out publishing per event: a batch that published per event would expose dimension maps that depend on an ordering the events themselves do not have, and that exist only because the events arrived together. Inside a chain there is no such ordering to expose, so a chain publishes nothing within itself. At a chain boundary there is one, and the map exposed there is not an intermediate at all — it is a complete canonical layout for a prefix of the submission, and it is precisely the map that would have stood had the caller split the submission at that boundary. Batching therefore still amortises the rebuild and the publication across everything it can amortise them across, and stops exactly where amortising would mean discarding an order.

Applying a chain as one plan is what the arrangement is for. Every operation in a chain names the positions it removes against one immutable entry layout; the union is marginalised in a single Schur complement, which is exact because Gaussian marginalisation composes (`thm:gaussian:marginalisation`); the standardisation vectors are compacted once over that same union. No operation can observe a layout another operation in its chain has already changed, because none of them changes it — the state changes once, at the end, for all of them. That is a stronger property than any per-event index arithmetic can be made to have, and it is what closes a family of staleness defects rather than an instance (`entry:assayer:wl-owner-dereg-scan`).

The predicate that admits a pair to one chain is conservative by construction: a pair is order-free only where the argument is made for it, and an unproven pair breaks the chain. Breaking is never wrong, because the operation that seals a chain begins from a freshly published layout, which is the state a submission carrying it alone would have handed it. Registrations are order-free with nothing, themselves included — how wide a registration is depends on live entity state, and where its coordinates land depends on the append — so a registration is a chain of one. That is what gives a same-identifier registration and retirement submitted together a defined behaviour without a special case: the registration publishes, and the retirement removes what it published.

Continuing past a failure is the other half — there is no useful place to stop, because the events are independent and abandoning the remainder would leave the batch half-applied with no way to express which half. The dimension invariant is what catches an inconsistency instead.

Two consequences are worth stating for a caller. The version counter advances once per chain rather than once per submission, so a submission of k chains publishes k snapshots at k consecutive versions before its completion signals. And the marginalisation diagnostics a result carries are the chain's rather than the operation's: one chain is one Schur computation over one union of positions, and there is no honest way to split its error partition back out per index set, because no per-index-set computation was performed. Each result names the chain it belonged to, so a consumer counting applications counts distinct chains rather than operations.

**Decision (Deregistration is destructive by default)** · `dec:construction:destructive-deregistration`

Deregistration marginalises the entity out of the models and drops its rows. Nothing is archived for a later return, and re-registering the same identifier produces a fresh entity rather than a restored one (`src/owner/lifecycle.rs`).

Destructive is the default rather than the only reading. The specification's hibernation is a variant of this protocol and not a replacement for it — the record *may* be stored instead of being dropped (`alg:registry:hibernation`) — so a host that wants the entity's own structure kept asks for it by name, and a host that says nothing gets the destructive removal. The default is the right way round because the archive is a storage cost that accrues in wall-clock time against an identifier that may never return, and a deployment should not pay it by omission.

What makes the default cheap is that the arrangement needs no accommodation: the marginalisation correction carries the departing dimension's information into the survivors, so what the archive adds is the entity's own structure, and the specification is explicit about how narrow that is (`cav:limitation:hibernation`). Deregistering destructively therefore loses the entity's self-structure and nothing else, which is what makes it a reasonable thing to do by default rather than a loss to be avoided.

The hibernating reading is stated in full at (`entry:construction:hibernation`).

**Remark (What the registration wait is waiting for)** · `rem:construction:registration-timeout`

Registering an identity dimension hands the graph owner a creation command and blocks on its acknowledgement (`src/api/lifecycle.rs`). The block is bounded by the host's configured figure, defaulting to ten seconds, and exceeding it does not report a slow registration: it returns the error that says the maintenance thread is gone. The figure is therefore a liveness bound and not a latency budget, and the difference decides what it has to be wider than — every acknowledgement a live owner would ever send, however busy, because a false positive here tells a host its identity layer has shut down when it has not.

Nothing in this package bounds the interval it must clear. The command is picked up on the owner's next pass, and a pass drains every dimension's observation queue, applies the deferred cache writes, recomputes and republishes each competitive set, and may apply the spatial decay (`dec:memory:maintenance-cadences`); commands already queued ahead are served first. None of that has a stated ceiling, so the default ten seconds is not derived from it. It is a shipped operating point chosen wide — orders above a pass that is expected to complete inside the wake cadence — and the honest reading is that it is generous rather than computed. That it is generous rather than computed is also why the figure is a host's to move: a bound no derivation fixes is one a deployment that knows its own owner's load may reasonably set for itself (`const:assayer:registration-acknowledgement-timeout-seconds-10`).

**Caveat (The registration timeout was declared twice and read once)** · `cav:construction:registration-timeout-shadowed`

The configuration surface carries `identity_registration_timeout_secs`, defaulted to ten seconds and refused at zero by the builder, and the wait now reads it (`src/api/lifecycle.rs`), (`src/config/types.rs`). Until the wait was pointed at that field it did not: the wait used a constant of its own, also ten seconds, so the two agreed by coincidence and a host that configured thirty still waited ten.

Of the two honest repairs — read the configured value at the wait, or withdraw the field so the figure is plainly a constant — the first was taken, on the ground that a bound no derivation fixes is one a deployment may reasonably set for itself (`rem:construction:registration-timeout`). The ten seconds survive as the default and nothing else, formed once at the configuration's own default and read at the wait through a single accessor, so there is no second figure left to disagree with the first.

The record is kept rather than struck because the failure it names is a shape this corpus has met more than once — a configurable no consumer reads is the same failure as a tolerance no assertion consumes (`cav:assayer:harness-unconsumed-tolerances`) — and because what made it survive is worth remembering: the field was defaulted, validated and asserted, and every one of those tests passed against a field nothing read. A surface is not connected because its value is checked.

**Table (The parameters the surfaces defer to)** · `tab:construction:parameters`

Every numeric default the runtime surfaces reason about is a parameter of this contract. The table names each group, what it governs, and where the code holds it; no value is transcribed, on the standing reasoning that a fact the code can answer should be made to answer it (`obs:assayer:adr-visibility-drift`) — and on the demonstrated cost of the alternative, which this record's own register records (`reg:construction:collapsed-initial-state`).

**Register (The initial state a registration creates a slot in)** · `reg:construction:collapsed-initial-state`

Two legacy contracts gave the same call opposite answers. One had registration create the slot with its bootstrap flag already set, and said so in its binding constraints and in the method's own documentation; the other had the constructor start the flag clear. Both were live public contracts describing one call, and they differed on what the call produces.

The second record also contradicted itself, asserting the set flag in a relates-to note and the clear flag in its verification table and its relationship table. The code adjudicates and starts it clear: the slot constructor sets the flag false, and registration activates a bootstrap accumulator only afterwards and only where the batch initialisation has already passed (`src/report/slot.rs`). The census recorded the divergence with its evidence (`reg:assayer:adr-contradictions-records`).

**Caveat (The schema is fixed once the instance exists)** · `cav:construction:schema-fixity`

The signal schema and the interaction templates are declared once and fixed thereafter (`req:host:schema-declaration`), which the specification also states of the schema itself (`req:signal:schema-fixed`). A host cannot add a signal, change a shape, or alter a template afterwards; axes and Sentinels are registered through their own declarations (`req:host:axis-registration`) and are not affected.

The boundary is real and a host will meet it. These properties determine the base feature layout that every learned parameter is indexed against, so changing one mid-session would invalidate the calibration buffer and every model at once — which is a fresh construction wearing a different name. Stating the limit here is better than discovering it as an absent method.

**Entry (Hibernation for deregistered Sentinels and axes)** · `entry:construction:hibernation`

Completed, and the register entry this deferral migrated from is retired at (`entry:assayer:defer-lifecycle-hibernation`). A Sentinel and an outcome axis may each be removed hibernating instead of destructively, and a registration of the same identifier before the archive expires re-extends the models with the entity's own aged block instead of with the prior.

The deferral was a definition STOP and it was a real one. The specification fixes the mathematics whole — the preserved payload is the mean sub-vector, the relevant precision and covariance rows and columns, and the standardisation entries; the restore ages that self-structure on both clocks; every cross-feature block is discarded and restored as zero (`alg:registry:hibernation`), (`cav:limitation:hibernation`) — and fixes nothing about the archive itself. It says the record *may be stored against the Sentinel identifier* and that restore occurs *before the store expires*, which names neither an encoding, nor a custody convention, nor an expiry clock, nor a duration. Choosing those was design rather than derivation, so nothing was built until they were chosen. What discharges the STOP is the minimal contract below: six clauses, each the narrowest answer that makes the specified mathematics executable, and none of them extending what hibernation preserves.

*Encoding.* The archive record uses the package's existing checkpoint encoding and carries a generation of its own. The two generations answer different questions and so cannot be one: the checkpoint's says whether this process can read the file at all, and the record's says whether a record inside a file it can read describes a block laid out the way this build expects. A record of another generation is refused and the registration takes the prior.

*Custody.* The archive is a field of the working copy and travels in the whole-state checkpoint. It never leaves the Assayer. That settles the writer question by construction — the single steward is the only writer (`dec:concurrency:single-steward`) — and it settles the persistence question the way every other piece of learned state is settled (`dec:durability:checkpoint-journal`). It is deliberately absent from the published snapshot, because no assessment or label has anything to ask of a block belonging to an entity that is not registered. Carrying it costs a format generation, and the no-migration policy applies unchanged: a checkpoint written before the archive existed is refused and the instance cold-starts, which leaves it with an empty archive — the state a deployment that has never hibernated anything is already in, so the refusal loses nothing.

*Expiry.* Wall-clock, configured, defaulting to ninety days, and named in the parameter table above. The clock is the persistent one rather than the label one because an archive's storage cost accrues in time whether or not the instance is processing anything (`dec:clock:two-domains`). The duration is a host's because how long a retired measurement surface's structure is worth keeping is a fact about a deployment's traffic and not about the mathematics; the ninety days are a shipped operating point and nothing more, in the same sense the registration wait's ten seconds are (`rem:construction:registration-timeout`). Both ends are refused at construction: a lifetime of zero is the destructive path wearing the hibernating path's name, and a lifetime past a year could never be reached, because every elapsed reading is clamped there before the comparison sees it (`dec:clock:embedded-clamp`).

Expiry is enforced without a clock of its own. The restore reads the same wall clock, so an expired record is refused whether or not anything has swept it; the sweep runs on the steward's own lifecycle pass and exists to stop the storage outliving the permission to use it. No background thread and no maintenance phase were added.

*Restore window.* Restore is legal only before the identifier is registered again, and a registration ends the archive's usability whatever it decides to do with the record: the registration *takes* the record from the archive rather than reading it. Without that, one hibernation would go on answering every later registration of the same identifier for as long as the lifetime allowed, which is a second entity inheriting a first entity's weights (`test:crate:re-registration-ends-the-hibernation-archive`).

*No replay.* The restore applies the specified decay treatment and nothing else. Each model ages its own block on its own label-indexed rate against the one time-indexed core rate, which is the pairing the forgetting-rate table already draws (`tab:risk:forgetting-rates`); the precision block is scaled by that factor and the covariance block by its reciprocal, which is the pairing bulk time-decay already uses and is what keeps the two exactly dual; the mean crosses unaged, because a decay of the posterior expresses a loss of confidence in an estimate rather than a movement of it. Every cross-feature block is restored as zero by not being written at all — the extension already zeroed it. No missed label is caught up and no other quantity is touched.

*Identity dimensions.* No payload. The algorithm names a Sentinel's block and the axis remark applies the same protocol to an axis (`rem:registry:axis-hibernation`); neither names anything for an identity dimension, and inventing one would be the design this entry declined to do under its own STOP. A deregistered dimension is relearned (`test:crate:identity-dimensions-carry-no-hibernation-payload`).

Two derivations were needed inside those clauses and both are stated rather than assumed. The first is what "the relevant rows and columns" means at implementation grain: the preservation scope answers it — the parameter relationships among the entity's *own* features — so the archived block is the square block those positions form among themselves, and a Sentinel's interaction features, which are couplings to another Sentinel, are outside it. The second is when an aged block is worth restoring at all. The live path applies the per-label rate and then holds every precision diagonal at or above the replenishment floor (`req:gaussian:prior-replenishment-floor`), so a block whose smallest diagonal would land below that floor after ageing has been forgotten in the only sense the model has, and the registration takes the prior instead. That test is also what keeps the arithmetic bounded: a factor small enough to sink the precision below the floor is a factor large enough to make the reciprocal-scaled covariance unusable.

The block is verified before it is transplanted, and that is a third question rather than a widening of the second. The floor test reads the block's smallest diagonal because that is the quantity the replenishment floor is stated in, and what it answers is whether the entity has been forgotten. Whether the block is a matrix the model may hold at all is not the same question and the diagonal cannot answer it: a strictly positive minimum diagonal is necessary for positive definiteness and is not sufficient for it (`req:gaussian:positive-definiteness`), so a block that passes the floor test at any floor below one can still carry a negative eigenvalue (`test:crate:hibernation-admits-a-block-on-its-spectrum`). The transplant is exact — the block is written over positions whose couplings the extension left at zero, so the matrix is block diagonal there and its spectrum is the union of the block's with the rest's — which means an indefinite archived block puts its negative eigenvalue into the live posterior directly. The archive crosses the persistence boundary in the checkpoint's own encoding, so it arrives on the same footing as the checkpoint and warrants the same verdict (`dec:posterior:cascade-never-fails`).

The verdict is taken of the record as a whole, at admission, where the other four refusals are. Forgetting is a property of one model against elapsed time, so it stays per model at the moment of transplant; definiteness is a property of the artefact, and the per-model ageing cannot change the answer, because scaling by a positive factor multiplies every eigenvalue by it and moves none across zero. A record with one indefinite block is a damaged record, and admitting its other blocks would be transplanting parameters out of an artefact already known to be damaged. Refusing costs one factorisation per archived block per registration and nothing else: the registration then extends at the prior, which is the fallback this entry already names for every other refusal, and which is a definite block by construction (`test:crate:indefinite-archived-block-leaves-the-registration-at-the-prior`).

The archive is refused where the arrangement has changed, which is the specification's own condition that the entity's configuration has changed. A Sentinel's slot widens with every spatial outcome axis and an axis's block widens with every identity dimension and every Sentinel, so the record carries the counts it was archived under and a registration creating a differently shaped block takes the prior (`test:crate:hibernation-refuses-a-changed-arrangement`). One consequence is worth naming: hibernating a *spatial* outcome axis rides on the layout permutation, which is separately known to refuse on that event because the map does not record which axes are spatial. The archive is taken before the marginalisation and is correct either way; the refusal is the pre-existing defect and hibernation neither causes nor repairs it.

The completion trigger is met. Focused tests hold the round trip against a hand-computed ageing on both clocks and per model (`test:crate:hibernated-sentinel-returns-aged-on-both-clocks`), the cross-feature zeroing against an established coupling (`test:crate:restored-sentinel-cross-feature-blocks-are-zero`), the expiry from both sides of its own boundary (`test:crate:expired-hibernation-archive-is-refused`), the axis protocol with its fresh prediction model (`test:crate:hibernated-outcome-axis-returns-with-its-own-block`), and the archive crossing a checkpoint whole (`test:crate:hibernation-archive-crosses-a-checkpoint`).
