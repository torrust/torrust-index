# Assayer integration tests · `reg:assayer:integration-test-catalogue`

The tests in this directory exercise the Assayer through its public surface. What each one establishes is written where the test is, in its own documentation comment, and the table at the foot of this file is generated from those statements rather than maintained beside them.

## Where the scenario matrix went · `sec:assayer:matrix-retirement`

This file used to be a scenario matrix: a long catalogue of numbered promises sorted into named divisions, with a hand-kept tracker at the top saying how many of them were witnessed. It was the largest test document in the workspace and the one (`sec:testdocs:monolith`) most changes. It does not survive as a document; every function it performed does, and this section says where each went so that a reader who remembers the old file can find what they came for.

The index from a promise to the tests covering it is now generated, twice over. Every source carrying a covered test holds an index of that file's tests, and every folder holding a source carries a readme with a matrix of the folder's — the one at the foot of this file among them. Both are computed from the labels and compared to the committed bytes on every run, so neither can drift from what the tests actually say.

The statements themselves moved into the tests. A scenario's promise is now the gloss standing above a test's own claim label, said once, where the test is; a promise several tests establish together is one statement minted and the rest citing it, which makes shared coverage a query rather than a reading of several files.

The promises no test carries did not move, because there was nowhere to move them to. They stand below as statements of intent.

The names the divisions gave their groupings are replaced by the areas the claims turned out to want, and each area's stake — why it exists, and what is lost if it fails — is written in the register (`sec:assayer:area-register`) the package [readme](../README.md) carries. Six of the twelve divisions were mixtures by the campaign's own study, two of them announcing it in the name and one defined as a residual of the others, so the replacement is a splitting rather than a renaming.

The mechanism cross-reference index answered one question — an implementor changed a module and wants to know which tests cover it — and that question is now answered twice without a document. Which tests cover a module is the module's own generated index and its folder's matrix. Which tests cover a concern that crosses modules is the claim area, censused by the linter's coverage report and reversed by its graph report. One of the index's twenty-five mechanism names has no area of its own and is worth saying out loud: concurrency and atomicity are claimed across the assessment path, the published snapshot, the owning thread and the ledger rather than gathered under one token, because they are a property several areas each have to keep rather than a subject any one of them is about.

The harness roadmap moved to the testing plan, which absorbs it and stays alive. Staging, dependency ordering, and which infrastructure work unblocks which untested promise are planning rather than indexing, and they belong in a plan.

The hand-kept coverage tracker went nowhere, because it was nowhere: it was derivable cell for cell from the status strings of the scenarios it counted, which made it an undeclared generated region rather than content. It is replaced by the linter's coverage report, which counts the same facts from the same census the check judges against — and which is what makes retiring this document safe, since a promise standing as an unwitnessed intent is a promise the report enumerates on every run.

## Statements of intent · `sec:assayer:intents`

Each statement below is a promise the system makes that no test yet keeps. They are minted as claims so that they are named, answerable, and countable: a claim no test carries is an intent, and the coverage report lists it as one until a test mints or cites it. Writing that test is the whole of what turns an intent into coverage — the statement stays exactly where it is, and stops being reported here.

That is the difference between an intent and a to-do notice. A notice says work is outstanding; an intent says what the system is supposed to do, in the same indicative voice a covered test's gloss uses, so it can be read, disputed, and witnessed without anyone reconstructing what was meant.

**Claim (The Assayer holds no mutable handle on a Sentinel)** · `claim:assess:no-mutable-handle-on-a-sentinel`

Nothing on the assessment path can reach into a Sentinel and change it: the type the interpretation layer holds offers no mutable handle, so no threshold can be set and no graph repartitioned from the side that is reading the measurement. The boundary is carried by the shape of the types rather than by discipline, so crossing it is a compilation failure rather than a corruption discovered a thousand labels later.

**Claim (Replacing a challenge tracker leaves the core belief untouched)** · `claim:channel:replacing-a-challenge-tracker-leaves-the-core-untouched`

A channel's challenge-effectiveness tracker can be replaced or reset mid-stream without moving anything in the core risk basis: assessing the same observation again afterwards yields the same fields it yielded before. Derivation supplied with the old challenge estimate replays the old reckoning exactly, and the new estimate is allowed to move only the action tags that are sensitive to challenge — which is what makes the tracker a component of the decision layer rather than a hidden input to the model.

**Claim (A hibernating Sentinel returns with its own weights)** · `claim:lifespan:a-hibernating-sentinel-returns-with-its-own-weights`

A Sentinel that is deregistered and later re-registered with hibernation gets its own slot weights back, aged by $\gamma^{n_\text{labels}} \cdot \gamma_t^{\Delta t}$ rather than reset to zero, while the weights another Sentinel learned during the absence stand undisturbed. Cross-terms between the returning Sentinel and anything admitted while it was away start from zero, because correlation between two measurement surfaces that never operated together is something the model has no evidence for.

**Claim (Marginalising a Sentinel leaves its information behind)** · `claim:lifespan:marginalising-a-sentinel-leaves-its-information-behind`

Deregistering an informative Sentinel does not throw away what it taught the survivors: the Schur complement hands its cross-information to the features that shared it, so their precision rises rather than falls when it goes. Discrimination on held-out traffic degrades gracefully instead of collapsing, which is the difference between retiring a data source and losing everything learned through it.

**Claim (An outcome axis nobody reports stays at its prior)** · `claim:lifespan:an-axis-nobody-reports-stays-at-its-prior`

An outcome axis that is registered and then never given a value stays exactly where it started — $\mu_a = 0$ and $B_a = \lambda_\text{prior} I$ — however many assessments pass through, and the dimensions other models hold for it stay at prior alongside it. Retiring such an axis marginalises cleanly and leaves no artefacts behind, so an axis declared in hope and never used costs nothing but its width.

**Claim (A competitive cell exits as another enters and the width adds up)** · `claim:identity:a-competitive-cell-exits-as-another-enters`

When volume moves from one entity to another under a fast-decaying identity dimension, the fading entity's cell is marginalised out and the rising one's is extended in, with cross-information transferring on the exit and the arriving indicator starting at weight zero. The dimension count stays consistent through the changeover: a competitive set that turns over is the ordinary operating case, not an event the model has to be rebuilt around.

**Claim (A mis-standardised arrival bootstraps back into scale)** · `claim:feature:a-mis-standardised-arrival-bootstraps-back-into-scale`

A Sentinel joining a trained deployment with z-scores in the range 5–15 is grossly mis-standardised on arrival, so its features enter carrying class priors and the per-Sentinel bootstrap at $\alpha_\text{boot} = 0.8$ pulls its standardisation into scale within about a hundred assessments. The leverage bound caps what any single observation can do during that window, so the cost of an arrival at the wrong scale is a short blind spell rather than a permanently skewed model.

**Claim (The Schur complement is the analytical marginal)** · `claim:bayes:the-schur-complement-is-the-analytical-marginal`

Removing a Sentinel by Schur complement on the precision, $B' = B_{kk} - B_{kr}B_{rr}^{-1}B_{rk}$, gives back exactly the marginal posterior obtained analytically from the full one — $(B')^{-1} = \Sigma_{kk}$ to floating-point tolerance, against a live posterior rather than a constructed matrix. This single identity is what the whole lifecycle algebra rests on: if it does not hold, every deregistration silently invents a different model instead of narrowing the one that was learned.

**Claim (A restored instance continues the run it was cut from)** · `claim:persistence:a-restored-instance-continues-the-run-it-was-cut-from`

An instance rebuilt from a checkpoint and its journal picks up where the crash interrupted it: model state, published risk basis, Ledger views, identity graph, companion trackers and health metrics all match, within tolerance, the continuation that never crashed. A configuration whose structure no longer fits the saved shape cold-starts rather than restoring onto it, while changes that are merely numerical restore as usual — warm-starting onto state whose coordinates now mean something else would be worse than starting cold.

**Claim (Restore-time decay is applied exactly once)** · `claim:persistence:restore-time-decay-is-applied-exactly-once`

The interval between a checkpoint being taken and its restore is discounted once, at restore, and labels replayed from the journal afterwards see $\Delta t \approx 0$ rather than being aged through the same gap a second time. Decay is applied lazily wherever a value is next touched, so an implementation that both discounted the outage and then charged the replayed evidence for it would quietly halve the very state the checkpoint exists to preserve.

**Claim (A stale adverse history dissolves without fresh labels)** · `claim:ledger:a-stale-adverse-history-dissolves-without-fresh-labels`

A burst of adverse labels into one cell leaves a Ledger contribution that thereafter decays along the analytic curve of the 29-day half-life, so once the live Sentinel reading has returned to neutral the risk estimate returns to baseline on the clock alone. Recovery cannot be made to wait for fresh eligible labels from the region, because a region under suspicion is precisely the one least likely to produce any.

**Claim (An entity that relocates is tracked across the move)** · `claim:identity:an-entity-that-relocates-is-tracked-across-the-move`

An entity that earns a high-risk rating in one region and then moves to another is followed coherently end to end: cells in the abandoned region exit, cells in the new one enter, ancestor routing keeps coverage unbroken across the handover, the new region earns its own rating, and the abandoned region's reputation dissolves. Each mechanism is promised separately elsewhere; what this adds is that they compose — there is no window during the move in which the entity is unrated because one layer has released it and the next has not yet taken it up.

**Claim (Three decay clocks run independently)** · `claim:ledger:three-decay-clocks-run-independently`

The same entity is aged by three separate clocks that do not contaminate one another: identity state at a 14-day half-life, Ledger entries at 29 days, and model uncertainty at 290 days, each tracing its own curve as virtual time advances. The three horizons are deliberate — a reputation should outlive a competitive cell and be outlived in turn by what the model has learned — and a shared clock would collapse that ordering into a single rate nobody chose.

**Claim (Label-indexed and time-indexed decay compose multiplicatively)** · `claim:numerics:label-indexed-and-time-indexed-decay-compose-multiplicatively`

Ageing by labels and ageing by elapsed time multiply rather than interfere: $\gamma_\text{eff}(n, \Delta t) = \gamma^n \cdot \gamma_t^{\Delta t}$, whichever order the two advance in. The class-balance trackers take only the first of these — they have no time-indexed decay at all — because a positive rate is a property of the labels seen and not of how long ago they arrived.

**Claim (A stream with no adverse outcome converges to near-zero risk)** · `claim:bayes:a-stream-with-no-adverse-outcome-converges-to-near-zero-risk`

Five thousand labels with $v \leq 0$ and not one adverse outcome drive $P_+ \to 0$, bind the positive importance weight against its ceiling of 100, and settle predictions at near-zero risk without the posterior degenerating. A rare $v > 0$ injection into that stream is caught by the leverage bound rather than being allowed to move the model by its full importance weight, so the first adverse outcome in a long benign run is evidence and not a shock.

**Claim (Discrimination is withheld until there are positives to discriminate)** · `claim:wellness:discrimination-is-withheld-until-there-are-positives`

Discrimination is reported as absent rather than as a number whenever fewer than three positive calibration labels have been seen. An area under the curve computed from one or two positives is arithmetic without meaning, and a host watching a dashboard cannot tell such a figure from an earned one — so the absence is reported explicitly instead.

**Claim (A divergent starved cell surfaces when labels are requested)** · `claim:guidance:a-divergent-starved-cell-surfaces-when-labels-are-requested`

A cell running an adverse rate of 0.15 against a much lower eligible base rate, with only three recent eligible labels behind it, comes back from a request for labels under starvation relief, scored by how far its rate exceeds the eligible base rate times how far short of the 200-label window it has fallen. Both conditions have to be present at once for it to appear at all: divergence with plenty of labels is a finding rather than a request, and starvation with an unremarkable rate is not worth an investigator's time.

**Claim (The importance ceiling, not the data, sets gradient balance)** · `claim:bayes:the-importance-ceiling-and-not-the-data-sets-gradient-balance`

At a positive rate of 0.1% the positive importance weight sits pinned at its ceiling of 100 with the negative weight near 0.5, leaving gradient balance around 16.7% — the ceiling binds, so the balance is chosen by configuration rather than by the class ratio. Raising the ceiling to 500 lifts the balance to about 33.3%, which is what makes the ceiling an operator's dial: it trades how far the rare class may be amplified against how much a single positive label may move the model.

**Claim (The leverage bound fires at cold start and rarely after)** · `claim:bayes:the-leverage-bound-fires-at-cold-start-and-rarely-after`

In steady state the leverage bound is a rare intervention — it clips roughly 2–8% of positive-valence labels and under 0.1% of negative ones — while over the first two hundred labels it fires on something like 30–60% of them. The bound is therefore a cold-start device that all but retires itself: a rate that stayed high would mean the model was being held back from evidence it should by then have been able to absorb, and one that started low would leave the opening labels free to dictate the posterior.

**Claim (Restriction opens a gap between operational and sister estimates)** · `claim:risk:restriction-opens-a-gap-between-operational-and-sister-estimates`

Where nothing is blocked, the operational and sister models see the same eligible labels and $\Delta(\phi) = \hat{\rho}_\text{inh} - \hat{\rho}_\text{opr}$ sits near zero; where high-risk traffic is blocked while investigated ground truth still reaches the sister, the gap opens positive and stays there. That gap is the measurable signature of restriction rather than a fault, and after a regime change the operational model's faster forgetting ($\gamma_\text{opr} = 0.9995$ against $\gamma_\text{inh} = 0.9998$) makes it the one that moves first.

**Claim (The anchor catches a regime change first)** · `claim:risk:the-anchor-catches-a-regime-change-first`

When the data generation flips and a previously benign class turns adverse, the fifteen-parameter anchor re-converges roughly forty times faster than the six-hundred-parameter sister, so its residuals fall while the sister's are still carrying the old regime. Coverage during a regime change is exactly what the anchor is small for: a model with few parameters can be wrong about detail and still be right about direction long before a rich one has been persuaded.

**Claim (A registration lifts the blend weight and labels lower it again)** · `claim:risk:a-registration-lifts-the-blend-weight-and-labels-lower-it`

Registering a Sentinel into a converged deployment, where the blend weight has settled near 0.05, raises that weight immediately: the sister's uncertainty on the shared subspace has genuinely grown, and the anchor is owed more of the estimate until it shrinks again. As labels accumulate the weight decays back towards a new asymptote, so the lift is a transient priced by evidence rather than a step the deployment never recovers from.

**Claim (Sentinel-specific uncertainty does not wake the anchor)** · `claim:risk:sentinel-specific-uncertainty-does-not-wake-the-anchor`

One Sentinel starved of data leaves the blend weight low as long as the shared subspace is well estimated: the anchor is woken by uncertainty in what the two models hold in common, never by uncertainty confined to a single Sentinel's own features. The anchor cannot see those features at all, so leaning on it there would substitute a model that knows nothing about the sparse surface for one that at least knows it is unsure.

**Claim (A measurement-only feature contradicts stale history)** · `claim:risk:a-measurement-only-feature-contradicts-stale-history`

The measurement-only anchor feature $\max_s \max_a z_{s,a}$ reads current Sentinel measurement and nothing else, so once a cell's live readings have normalised it disagrees with risk features still carrying the cell's stale adverse history. That disagreement is fed to the drift accumulator as a persistent discrepancy until the Ledger decays — which is how contamination announces itself while eligible labels are too sparse to settle the question.

**Claim (A two-action channel crosses over at the Q-matched half-power boundary)** · `claim:resonance:the-two-action-crossover-sits-at-the-q-matched-half-power-boundary`

A channel offering nothing but Allow and Block has exactly one crossover, and it sits at the Q-matched half-power boundary the specification fixes in closed form. With no intermediate action to occupy the middle of the posture axis, that single point is the whole of the channel's policy, so where it falls has to follow from the formula rather than from wherever the neighbouring regimes happened to end.

**Claim (A trickle of untargeted challenges still sharpens belief, and still stops short of a usable estimate)** · `claim:risk:a-trickle-of-untargeted-challenges-sharpens-belief-and-stops-short-of-a-usable-estimate`

At 0.08 contributing labels a day a challenge tracker starting from a uniform prior has seen about twenty labels after two hundred and fifty days, and decay between arrivals leaves about twelve of them standing: a total pseudo-count near 14 and a variance near 0.017, against the uniform prior's 0.083. Evidence arriving that slowly still sharpens belief about fivefold rather than leaving it at the prior, and that is the whole of what it does — twenty effective observations are never reached at this rate, the ceiling being a pseudo-count near 19. The claim was minted on the decay-free arithmetic; its numbers were wrong, and its label asserted the accumulation those numbers appeared to show. Both are corrected here, and what the claim was minted to say about a trickle moving belief survives the correction. A host override supersedes the tracker in the derivation the moment it is set, while the tracker goes on accumulating underneath it, so the override is a substitution for the estimate and not an end to the learning that would replace it.

**Claim (Injected pseudo-counts are clamped at a thousand)** · `claim:risk:injected-pseudo-counts-are-clamped-at-a-thousand`

Evidence injected directly into a challenge tracker is capped: five thousand failures land as exactly one thousand, and the tracker's state afterwards holds that thousand and nothing more. The clamp is announced with a warning rather than applied silently, because a host that asked for five thousand and quietly got a fifth of it would otherwise go on reasoning about a prior it does not have.

**Claim (Silence inflates the reported uncertainty by the staleness factor alone)** · `claim:risk:silence-inflates-reported-uncertainty-by-the-staleness-factor`

An estimate that goes unlabelled reports more uncertainty for exactly as long as it is left alone and changes in no other way: the inflation is $1/\gamma_t^{\Delta t}$, so a hundred hours at a temporal factor of 0.9999 leaves the reported figure $(1/0.9999)^{100} \approx 1.01$ times the value the published snapshot carried, to floating-point tolerance. Staleness is therefore a computed quantity a host can reproduce from the elapsed time, not a guess the system makes on its behalf.

**Claim (A concurrently updated ledger average reads whole or not at all)** · `claim:ledger:a-concurrently-updated-average-reads-whole-or-not-at-all`

A cell average that flips from 0 to 0.5 while an assessment is reading it yields either the value before the label or the value after it — over a hundred thousand racing reads, never a torn intermediate. Assessment runs from every request thread a host has while labels land continuously, so a half-written average would enter the feature vector as a number no cell ever held and no later reader could account for.

**Claim (Two entities sharing a cell are separated by identity alone)** · `claim:identity:entities-sharing-a-cell-are-separated-by-identity-alone`

Two entities that always land in the same Sentinel cell but always draw opposite outcomes are told apart almost perfectly after five hundred labels — discrimination close to one — while that shared cell's own adverse average sits at one half, having learned nothing about either of them. The geometry a Sentinel reports cannot distinguish entities that occupy the same region, so where the distinction exists at all it is the identity features that carry it.

**Claim (Retiring an uninformative Sentinel costs no discrimination)** · `claim:wellness:retiring-an-uninformative-sentinel-costs-no-discrimination`

A Sentinel whose contribution reading has fallen below its threshold (`def:monitoring:slot-contribution`) can be taken out without the model getting any worse: deregistering it leaves discrimination where it was. The reading is what makes that decision available in advance, because it is the removal cost itself and not a proxy for it — the loss the score would have carried without the block, against the loss it carried with it — so an operator acts on the quantity the deregistration will produce rather than on a number that merely correlates with it.

The reading it replaced could not support this. Weight mass (`def:monitoring:encoding-effectiveness`) gave a hash-fed Sentinel between $0.76$ and $1.05$ of a perfectly predictive control's figure while removing that Sentinel cost the score between a fraction of a percent and a few percent of its loss, so a retirement taken on weight mass was being taken on a number that had stopped tracking the cost by the time it mattered. What is still open is the last step: that the loss cost being nothing implies the discrimination cost is nothing too. Log loss and discrimination are different functionals of the same score, and nothing here has measured a deregistration against the second.

**Claim (A tenfold base-rate shift trips the cumulative sum and resets calibration)** · `claim:wellness:a-tenfold-base-rate-shift-trips-the-cumulative-sum-and-resets-calibration`

A base rate moving from 5% to 50% over five hundred labels, after a thousand labels of stability, drives a cumulative sum past its threshold of $h = 10$, and a calibration displacement past 0.1 forces a drift reset. Drift detection has to fire on a shift of that size while it is still under way; a detector that only resolved it afterwards would leave the intervening decisions calibrated to a world that had already gone.

**Claim (Recent discrimination parts from the lifetime figure under drift)** · `claim:wellness:recent-discrimination-parts-from-the-lifetime-figure-under-drift`

Under a shifting base rate the discrimination measured over the recent window diverges from the figure taken over the whole buffer by more than 0.1. Holding the two views side by side is what makes drift visible at all: a lifetime average absorbs a recent collapse and keeps reporting the health the model used to have.

**Claim (Without refactorisation the inverse pair drifts apart)** · `claim:linalg:without-refactorisation-the-inverse-pair-drifts-apart`

With exact refactorisation suppressed, the precision and covariance matrices stop being each other's inverse by a margin that grows as labels arrive: $\|B\tilde{\Sigma} - I\|_F$ climbs steadily across five thousand labels rather than settling. The incremental updates are individually sound and jointly lossy, so the sync error is the accumulating quantity the recomputation schedule exists to answer.

**Claim (A conditioning estimate past a hundred thousand forces a refactorisation)** · `claim:bayes:a-conditioning-estimate-past-a-hundred-thousand-forces-a-refactorisation`

An estimated condition number above $10^5$ brings the adaptive recomputation forward, and the exact refactorisation it performs returns the sync error to near zero. Conditioning is the observable that stands in for accumulated damage, so the schedule is driven by how far the matrices have actually gone rather than by a fixed count of labels that would be too eager on easy data and too late on hard.

**Claim (A systematically mislabelled entity parts from the aggregate within ten labels)** · `claim:wellness:a-systematically-mislabelled-entity-parts-from-the-aggregate-within-ten-labels`

An entity whose outcomes are consistently recorded as the opposite of what they were is flagged after ten labels, its per-entity concordance having fallen more than 0.25 below the aggregate figure. Ten labels is few enough that the damage is still local to that entity, which is the window in which a host can still go and look at where its ground truth comes from.

**Claim (A concordance flag names a discrepancy without attributing a cause)** · `claim:wellness:a-concordance-flag-names-a-discrepancy-without-attributing-a-cause`

The flag says that one entity's outcomes disagree with the model far more than the population does, and it says nothing about why: systematically wrong labels and genuine unpredictability look identical from inside, and the system does not claim to tell them apart. Naming the discrepancy honestly and stopping there is what makes the flag a prompt for enquiry rather than an accusation a host would be wrong to act on directly.

**Claim (One investigated label moves every subsystem at once)** · `claim:labelling:one-investigated-label-moves-every-subsystem-at-once`

A single request that was challenged, passed, then investigated and recorded with established ground truth moves the whole engine on that one label: both core models shift, the channel's challenge counts advance, the ledger updates at every depth of the reported chain, the identity cells the request landed in update, its outcome axis is recorded, and the entity's next estimate rises accordingly. Each of those movements is promised on its own elsewhere; what is promised here is that they hang off the same label, so no subsystem sits quietly off the investigation path.

**Claim (One corrupted label in every two hundred costs almost nothing)** · `claim:wellness:one-corrupted-label-in-two-hundred-costs-almost-nothing`

Corruption at a rate of one label in two hundred stays below the per-entity concordance threshold and inside the cumulative sum's allowance, so no integrity diagnostic fires, and over ten thousand labels discrimination falls by only a hundredth or two. Forgetting ages each bad label out and the leverage bound caps what any single one can move, so noise at this level is absorbed rather than compounded — which is why it can be left unalarmed on without the damage accumulating in the background.

**Claim (Cross-Sentinel correlation is caught only once the interactions converge)** · `claim:wellness:cross-sentinel-correlation-is-caught-only-once-interactions-converge`

Traffic that looks ordinary to each Sentinel taken alone, and is suspicious only in the correlation between them, evades detection while the interaction features are still unconverged at two thousand labels and is detected by eight thousand. Joint structure is learned rather than given, so detecting it carries a warm-up cost that a host running a fresh deployment should expect rather than read as a failure.

**Claim (Sparsely reporting Sentinels ill-condition the precision matrix)** · `claim:linalg:sparsely-reporting-sentinels-ill-condition-the-precision-matrix`

A measurement surface where a third of the Sentinels report on only 3% of requests leaves the precision matrix badly conditioned once the model has converged, with $\kappa(B) > 10^4$. Coordinates that are almost always absent are almost never observed jointly with anything else, so the directions they span stay poorly determined however many labels the rest of the model has seen.

**Claim (Ill-conditioning is paid for in recomputation cadence and per-label cost)** · `claim:audit:ill-conditioning-is-paid-for-in-recomputation-cadence-and-per-label-cost`

Conditioning that bad shortens the recomputation interval to roughly every three hundred labels and raises the per-label cost by a third to a half. The adaptive schedule keeps the model correct under sparse reporting by spending time, so the cost of a measurement surface is a function of how reliably it reports and not only of how wide it is.

**Claim (Signals and competitive cells stand independently)** · `claim:identity:signals-and-competitive-cells-stand-independently`

Neither the signal cache nor the competitive cell set is a precondition for the other: an entity holding persistent signals with no competitive cell has its signals available as usual, and an entity holding a competitive cell that the cache has since evicted keeps a working cell indicator with its signal block zero-filled. The two structures fill and empty on their own schedules — eviction on one side, promotion on the other — so every combination of present and absent has to be an ordinary assessment rather than a case nobody arranged for.

**Claim (A wide pool churning at random keeps its width and its inverse pair)** · `claim:lifespan:a-wide-pool-churning-at-random-keeps-its-width-and-its-inverse-pair`

Eight Sentinels cycling in and out under random eviction for a hundred rounds leave the published feature layout exactly as wide as the registrations standing at each round imply, and leave the precision matrix and its maintained inverse within the synchronisation error their width allows (`def:monitoring:synchronisation-error`). The churn test the corpus already has is a lightened variant of this, and says so in its own comment: a pool of four names, eviction in a fixed rotation, and assertions that each reckoning is finite and the health report clean. What that establishes is that churn does not crash the model. What it cannot establish is that the layout still matches what is registered, or that the two halves of the inverse pair are still each other's inverse after the marginalising and extending churn generates — both of which fail quietly, by a column or by a slow accumulation, rather than by a panic. Random eviction is what stops the exit order being a schedule the code could come to depend on without anyone choosing it, and asserting the dimension count and the Frobenius departure directly is what turns a crash test into a statement about width and about drift.

## Integration test matrix · `tab:assayer:integration-test-matrix`

**Table (Integration test matrix)**

| Test | Area | Claim |
|------|------|-------|
| (`test:integration:request-context-builder`) | assess | A request begins as its entity and nothing else: the coordinate map and the signal map both start empty, and the entity's bytes come through unaltered. Nothing is inferred on the host's behalf, so an attribute absent from a request is absent from the assessment rather than silently defaulted to something the host never said. |
| (`test:integration:request-context-with-signals`) | assess | Signals attach to a request by name and keep the value the host supplied — a bare number becomes a numeric signal of exactly that magnitude, negative values included. Nothing is rescaled or clamped at attachment time, so whatever encoding the schema later applies is applied to the host's own number and can be reasoned about from it. |
| (`test:integration:request-context-with-sentinels`) | assess | One request can address several Sentinels at once, each under its own identifier, and each coordinate survives the full width of the hash space untruncated. An entity sits at a different place in every measurement space, so the coordinates must be kept apart and kept whole — a narrowed coordinate would point at the wrong cell in that Sentinel's tree. |
| (`test:integration:request-context-combined`) | assess | Coordinates and signals live in separate stores, so a host may interleave the two kinds of builder call freely and end with both counts intact. Real call sites assemble a request from several sources in whatever order the surrounding code makes convenient; a builder where ordering mattered would drop attributes depending on how the caller happened to be written. |
| (`test:integration:assessment-shared-state-trait-is-object-safe`) | assess | The shared-state interface can be named behind a trait object, which the compiler will only accept if every method on it is dispatchable dynamically. That keeps the interface within reach of a host that chooses its state implementation at run time or stores several behind one type, rather than confining it to callers that can monomorphise. |
